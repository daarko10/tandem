## 1. Goal

From the side chat, as the desktop app does but sized for a plugin's tool window: click the context ring to see what fills the context window, category by category, with the MCP tools, memory files, skills and agents behind the numbers; type `/usage` (or `/cost`) and get a card with this session's cost, times and per-model tokens and what has been using the plan's limits on this machine; open `+` for files or photos, a folder, the slash commands, the connectors and the session's plugins with their skills. Every number comes from the CLI's own output: a control response (`get_context_usage`, `get_usage`), a local command's line, `system/init` or the `initialize` answer. Tandem never reads credentials, never calls Anthropic's API and never computes an account limit (hard rule 3); a part the CLI cannot provide over stream-json is left out or deferred. Nothing runs on the EDT: every request is written and answered in the session's scope, payloads decode on `Dispatchers.Default`, file checks run on `Dispatchers.IO` (hard rule 1). Every failure shows (hard rule 5); every protocol change has a fixture test and `Unknown(raw)` never throws (hard rule 6); no string says "Claude Code" (hard rule 8).

Sections 12 to 16 answer the owner's second Mac test. While Claude works, Enter sends a message the CLI reads at its next step, and Ctrl+Enter (⌘↵ on macOS) queues one for after the turn, each drawn as a pending bubble until the CLI takes it (12). Every ended turn's reply can be forked, not only the latest (13). Shift+Tab in the composer cycles the permission mode, as in the CLI, through a Keymap action (14). A light band sweeps the working row's label beside the orbs 0.1.2 draws, and a streaming thinking row's label, unless `Reduce motion` is on, and nothing of it runs while nothing works (15). The /usage card shows more of what the CLI reports, and the ring leads to it (16). The same rules hold: every signal comes from the CLI's own lines, recorded in a fixture or marked otherwise; nothing waits on the EDT; every failure shows.

## 3. What the user sees

### 3.1 The context popover

**Opening.** The footer's context ring (polish 2.3: drawn once the tokens and the window are known, `ContextFormat.fraction`) opens its popover as today: click, Enter or Space; Esc or a second click closes it; it closes when the AWT focus leaves the tool window's panel (`focusLeft`). Placement unchanged: `AboveAnchor(alignEnd = true)` 8 dp above the ring. Width: `min(360 dp, chat column − 32 dp)`, at least today's 280 dp. Height: at most 60 % of the tool window's height (`ChatScreen` measures it and passes it down), scrolling past that. Today's one line (`Context window` and the value) becomes the header of the breakdown.

**Contents, top to bottom** (desktop frames: the popover opens compact, with a header, a thin segmented bar, a chevron and a button; the rows per category and the expandable groups appear once the chevron is clicked):

1. **Header**: `Context window` (dim) at the start, the value at the end. With a breakdown: `formatTokens(totalTokens) / ContextFormat.formatWindow(maxTokens) (<percentage>%)`, `percentage` being the CLI's own integer (`parity-context:17`: `totalTokens` 38032, `maxTokens` 1000000, `percentage` 4 → `38.0k / 1M (4%)`). Before the first answer: `ContextFormat.value` of the ring, so the header never waits. While a request runs with older rows shown, the header gains ` · Updating…`; with no rows yet, a line under it reads `Loading the breakdown…`. The header row is also the toggle of the category list (items 3 and 4): `›` collapsed, `⌄` expanded; the list is collapsed each time the popover opens, as the desktop's is, which keeps the first view small in a side chat; Enter, Space or a click toggles it and the popover stays open; `contentDescription = "Context window categories"`, `stateDescription` `Expanded` or `Collapsed`. The header, the status line (loading, error, stopped), the bar and `See detailed breakdown` show in both states. The open state lives in the popover's controller, one per open popover, so it is tested without Compose (9.4).
2. **Segmented bar**: 4 dp high, full width, rounded, over a track in the ring's `dim` colour at 30 % alpha. One segment per `used` category, in row order, `tokens / maxTokens` of the width (at least 1 px for a non-zero row). Colours are Tandem's own (`TandemColors.contextTone`, light and dark): `messages`, `mcp_tools`, `memory_files` and `system_prompt` each get one (the desktop colours only those four); every other used row, buffer and deferred rows are the neutral grey; free space is the track. The CLI's `color` values are TUI theme keys, not colours (`promptBorder`, `purple_FOR_SUBAGENTS_ONLY`, probes 2.1), and are ignored.
3. **Category rows**, one per category with `tokens > 0` (empty rows are absent on the wire anyway, probes 2.1): an 8 dp swatch in the row's colour (hollow for free space), the CLI's `name` verbatim, the tokens (`formatTokens`), and the share of `maxTokens` to one decimal (`0.3%`), as the CLI's own `/context` table prints it (`parity-context:24`); a deferred row (`kind == "deferred"` or `isDeferred`) shows `—` for the share, since it counts toward neither the total nor the window (probes 2.1). Order, as the desktop's: `used` rows by tokens, largest first; then `buffer`; then `free`; then `deferred` by tokens; then any other `kind` in the CLI's order (shown, never hidden: hard rule 5). Rows are matched on `id` (colour) and `kind` (order), never on `name`; an unknown `id` is grey, an unknown or missing `kind` sorts last.
4. **Groups**, collapsed when the popover opens, each a header row with `›` (collapsed) or `⌄` (expanded), the title, the group's total tokens and its item count; Enter, Space or a click toggles it and the popover stays open. A group is drawn only when it has items:
   - `MCP tools` (`mcpTools`, `parity-context:17`): `<server> · <tool>`, the tool part being the name with `mcp__<serverName>__` removed (the raw name when it lacks that prefix), and its tokens; a tool with `isLoaded:false` is drawn in the dim tier. The total sums every listed tool, loaded or not (the desktop's group total includes the deferred tools). The desktop shows human tool titles; the answer has none (probes 3.3), so names stay plain.
   - `MCP server instructions` (`mcpInstructions[{serverName, tokens}]`, **docs only**): the server's name and its tokens.
   - `Memory files` (`memoryFiles`, `parity-context:17`): the path with the user's home shown as `~` and a path under the project root shown relative to it (string prefixes only, no file access), one line, ellipsised in the middle; the full path and its `type` in the tooltip; tokens.
   - `Skills` (`skills.skillFrontmatter`, `parity-context:17`): the skill's name (plugin skills keep their `<plugin>:` prefix) and tokens.
   - `Custom agents` (`agents[{agentType, source, tokens}]`, **docs only**): the `agentType` and its tokens, the `source` in the tooltip.
   Items keep the CLI's order. At most 100 items are drawn per group, then a dim `and N more` (the owner's frames show a group of several hundred tools). The line does not say where the rest are: the `/context` report behind `See detailed breakdown` lists every MCP tool in the one recording, which has a single tool (`parity-context:24`); whether it lists, caps or groups several hundred is **unrecorded** (11 item 4).
5. **`See detailed breakdown`**: closes the popover and sends `/context` to the session as a prompt (`SessionManager.send(id, "/context")`; the draft and the attachment strip are untouched). The CLI answers it locally, with no model turn (`parity-context:24`, result `num_turns:0`, `duration_api_ms:0`, `:25`), and the reply is the existing local-command notice (MCP 3.5) whose `runCommand` is `context`; that one notice kind renders its text with the chat's Markdown renderer (`TandemMarkdown`, as replies are) instead of plain text, so its tables read as tables. The transcript keeps the same markdown (`transcripts/parity-context.jsonl:30`), so a reload shows the same row. While a turn runs, or a message waits in the CLI's queue (12), the item is disabled and reads `See detailed breakdown (after this turn)`; the user sends `/context` after the turn (or, with D8's **after the turn** outcome for `queue-later-command`, the composer queues it `later`, 12.1); the popover keeps one path. Why `/context`: what the desktop button opens is unknown (probes open question 5); `/context` is the CLI's own detailed report, it costs no model turn, and it stays in the session's history.

**Errors** (under the header, `text.error`, each with `Retry`): `Could not load the breakdown: <error>`, the CLI's text verbatim (a CLI that lacks the request answers `Unsupported control request subtype: get_context_usage`, the shape recorded for another subtype at `parity-context:19`); `Could not load the breakdown: the CLI's answer had no categories` for a success without a `categories` array; `The CLI did not answer within 30 s.` The header keeps the ring's numbers, and rows from an earlier answer stay below the error, dimmed. A stopped session (no process; the ring stays drawn from `ChatState.context`): the last breakdown if one was fetched, dimmed, and `The session is not running. The breakdown updates with the next prompt.`; no request.

**When the data is fetched, and why.**

- **On open**: one `get_context_usage` without `detail` (the CLI's `full`, the estimate that has a Messages row, which the desktop shows; `summary` has none and other numbers, `parity-context:17` against `:18`).
- **After each turn, while open**: a new request whenever `ChatState.turnsEnded` changes. The numbers move at turn ends: after a turn `totalTokens` equals that turn's `message_start` input and `result.first_request_input_tokens` (`parity-context:8`, `:15`, `:17`), and the ring already follows `message_start` meanwhile; values during a running turn are not recorded, and whether the CLI answers mid-turn is unrecorded (11 item 2). A request sent mid-turn that times out shows the timeout; the refresh at the turn's end retries by itself.
- **Never while closed**: no polling. The SDK says `full` counts each category with the token-count API; its latency and whether it counts against the plan are unmeasured (probes open question 1).
- **One in flight per session**: a refresh asked while one runs runs once after it.
- **Kept**: the last answer is kept in `ChatState.contextBreakdown`, so a reopened popover draws it at once and shows ` · Updating…` while the new one runs. It is not kept across a reload (the requests leave no trace on disk, `transcripts/parity-context.jsonl:22-25`).
- **Off the EDT**: the request runs in the session's scope, its payload decodes on `Default`, the controller builds the popover model on `Default`; the popover only collects a `StateFlow`.

**Reuse of the ring.** `ContextRing`, `ContextFormat.value` and `ContextFormat.fraction` keep drawing the ring and its tooltip unchanged; `ContextFormat` gains `percentOf(tokens, max)` (the one-decimal share) and the header reuses `formatWindow`. The popover replaces the `passiveItem` in `RingControl`'s `if (open)` branch; the ring's open state, keys and focus handling stay as they are.

### 3.2 The /usage card

**Trigger.** `/usage` is a built-in with an empty hint, so the palette (or Enter on the typed text) sends it at once (MCP 3.4); nothing new is intercepted. While Claude works it is sent with `priority:"later"`, to run once the turn has ended, only when D8's `queue-later-command` shows a `later` local command doing that (**unrecorded** today: `parity-usage:22-23` was sent while idle); until then it is refused while busy with 12.2's notice, the draft kept, and the user sends it after the turn (12.1). The CLI answers it locally: a synthetic assistant line with the text, `local_command_run:{command:"usage"}` (`parity-usage:22`), then a `result` with `local_command:"usage"`, `num_turns:0` (`:23`). `/cost` resolves to the same command (`local_command_run.command:"usage"`, `:28`). Today that line is a local-command notice (MCP 3.5). New: when a **stream** line has `local_command_run.command == "usage"` (so `/cost` too), no `parent_tool_use_id` and a `uuid`, its notice carries a usage card (keyed by the line's `uuid`), and on the `result` that ends that local turn (`local_command:"usage"` or `"cost"`, `:23`, `:29`) `ClaudeSession` asks the CLI for the structured numbers: `get_usage` with `skip_behaviors:true` (the session block, answered without the scan, `:16`), then `get_usage` (with the scan of this machine's transcripts, `:17`). The fetch waits for that `result` because the probes sent `get_usage` only between turns (`:16`, `:17`); whether the CLI answers it before the local turn's `result` is unrecorded, and waiting costs nothing (the `result` follows the line at once, `:22` → `:23`). A process that ends before that `result` fetches nothing, and the card's parts read `The session has ended.` The card is drawn in place of the notice's plain text.

**Why send-and-enrich and not intercept** (probes 3.4, options a and b): sending keeps the command in the CLI's transcript and history (`transcripts/parity-usage.jsonl:29-30`), a resumed session shows the CLI's text (the card needs live answers; on reload the row is the plain notice of today), and a CLI that lacks `get_usage` or answers an error still leaves the user its own text. Intercepting would lose all three.

**Layout.** A bordered box in the chat column (the polish cards' frame, 6 dp radius, 12 dp inside). Sections are stacked and every line wraps; nothing sits side by side, so the card reads at the tool window's narrowest width.

- **`This session`**: one wrapping line of label-value pairs: `Est. cost $0.15` (`session.total_cost_usd`, which equals the last `result.total_cost_usd`, `:14`; two decimals, `<$0.01` above zero and under half a cent; "Est." because the CLI's figure is its own estimate from a bundled price table, not billing data, docs), `API 4s` (`total_api_duration_ms`, `formatElapsed`), `Wall 9s` (`total_duration_ms`: the CLI reports wall time, `Total duration (wall)` in its own text, `:18`/`:22`; the desktop's "Active" has no source). A value the CLI leaves out is left out; with none of the three, the line is left out. Then `Prompt cache` followed by the rest of the CLI's own `Prompt cache (main):` line from the notice text, verbatim (`1 request · 0% of input tokens from cache · no misses · ...`, `:22`): the only place the CLI states a cache share (probes 2.2); the row is left out when the text has no such line. A number derived from `model_usage` waits for a recording with a non-zero cache read (probes 3.3).
- **`Breakdown`**: one block per model in `session.model_usage`, the session's active model first, then the CLI's order (the helper model is in the CLI's own totals, `:16`, so it is listed): the model's label (the footer's label of the `ModelOption` that resolves to it, else the wire id) and its cost (`costUSD`, same format), then `Input`, `Output`, `Cache read`, `Cache write` (`inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`, `formatTokens`). - **`What's using your limits?`**: a two-button `SegmentedControl` `24h` | `7d` (`behaviors.day`, `behaviors.week`; `:17`), `24h` selected first; the choice is per card and not saved. Collapsed, unless the session block failed or the text has a line the card does not account for: a non-blank line that is none of the CLI's `Total cost:`, `Total duration (API):`, `Total duration (wall):`, `Total code changes:`, `Usage by model:` and `Prompt cache (main):` lines (`parity-usage:22`) nor an indented model line under `Usage by model:` (`undrawnCliLines`, 4.3). ### 3.4 Add folder

**Choosing.** `FileChooserDescriptorFactory.createSingleFolderDescriptor()` titled `Add Folder`, shown with `FileChooser.chooseFile(descriptor, project, null)` (a modal dialog; it reads nothing itself) as an EDT event of its own after the menu's click, exactly as the base opens the image chooser (`ComposerImages.chooseImagesLater`: `invokeLater(task, ModalityState.defaultModalityState(), project.disposed)`). Never inside the Compose click, nor in a coroutine launched from composition: there the modal loop re-enters the scene's effect dispatcher and the chat stops painting, the 0.1.1 picture freeze (`6cb1973`; `ComposerImages.chooseImages`' KDoc forbids both). Only the chosen path then goes to a coroutine, for the checks on IO and `manager.addFolder`. The test-only system property `tandem.addFolder=<path>` returns that path instead, since IDE tests cannot drive the native chooser; it goes through the same posted event. Cancel does nothing.

**Checking**, on `Dispatchers.IO`, in this order, each refusal a composer notice (the `InlineWarningBanner` above the box that attachment refusals use, polish 2.7):
1. Not a directory any more: `Could not add <path>: it is not a folder.`
2. `toRealPath()` (macOS keys paths on their physical form, `/private/tmp/...`, CLAUDE.md "macOS", `docs/protocol.md` 11.1), compared with the project's real root: the root itself or a folder under it → `<name> is inside the project, so Claude can already use it.` Nothing is sent. A stream-json session can only register a subfolder of its working directory (`register_repo_root`, `parity-add-dir:10`, `:12`), and that folder is readable already; loading its own `.claude` is deferred (2.2).
3. Already added to this session (same real path): `<name> is already added.`

**Mechanism: the CLI's `--add-dir` on the next spawn.** A running session cannot gain a folder outside its working directory: `/add-dir` answers `unavailable_headless` (`parity-add-dir:6`), `register_repo_root` refuses it (`:12`), `add_directory` only takes `/uploads/` or `/outputs/` (`:13`). The CLI takes `--add-dir <dir>`, repeatable, at spawn (docs). So the folder joins the session's list as `PENDING`; if the process is idle the handle stops it now (`SessionHandle.stopIfIdle`, the same stop the live-session cap uses, which settles the chat and loses nothing: the next prompt resumes the same session, `docs/design.md` "Key choices"); while a turn runs, a card waits or a prompt is queued, it stops as soon as the session is idle. A session with no process stops nothing. The next spawn passes `--add-dir <real path>` per folder, in the order added, after `--resume <id>` (4.1). This is **unrecorded**: slice D0 records a spawn with `--add-dir`, a `--resume` respawn adding a second one, Tandem's fork argv with a folder, and a `--resume` respawn leaving the first one out, before any of this ships (hard rule 6; probes 4 item 4). If that recording shows the CLI refusing it, or a resume with a new `--add-dir` losing the session or its transcript, `Add folder` stays out of the menu and this section is revised.

**Confirming.** Each `system/init` of a process spawned with folders lists `additional_directories` (recorded for `register_repo_root`: `[]` at `:5`, the folder at `:17`; for `--add-dir` **unrecorded**, D0 checks it). After that init the handle compares each folder with the list, on IO (string equality, then `Files.isSameFile`): found → `ACTIVE`; not found → `MISSING` and the WARNING notice `The CLI did not add the folder <path>.` once per folder per spawn (hard rule 5). It also checks the other way, after each init of any process once a folder was removed from the session: a removed folder that is not among the spawn's folders but that the init still lists raises the WARNING notice `The CLI still lists the removed folder <path>.`, once per folder per spawn (hard rule 5: the user must not believe a folder gone while the CLI can still read it). Should D0 show that `--add-dir` folders never appear in `additional_directories`, the folder turns `ACTIVE` when the spawn's first init arrives, and the plan says so.

**Shown in the session.** A strip at the top of the composer box, above the image thumbnails: one pill per folder, a folder icon, the folder's name, and a 16 dp `×`. Tooltip: the full path (the home as `~`) and the state: `Applies with the next prompt.` (`PENDING`), `Added to this session.` (`ACTIVE`), `The CLI did not add this folder.` (`MISSING`, the pill in `text.error`). `×` removes the folder the same way (stop when idle, the next spawn without it). That the CLI then no longer has the folder is **unrecorded**: a `--resume` might restore a session's folders, as `/add-dir`'s `source:"session"` folders may be (probes 2.3, docs). D0's last process (a `--resume` with the second folder only) records it, and the check under "Confirming" catches it later. Should D0 show the CLI keeping a removed folder, or no `--add-dir` folder ever listed (so a removal cannot be seen), the `×` stays out (a folder then leaves with a new session only) and this section is revised. A respawn reconnects the session's MCP servers and plugins, so the first prompt after a change takes longer; the `PENDING` tooltip says when it applies.

**Lifetime.** As long as the session's `SessionHandle`: kept across the cap's stops and resumes; a fork starts with its parent's folders, a fork at a reply (13) included (D0 also records Tandem's own fork argvs, `--resume <id> --fork-session --session-id <new id>` and the same with `--resume-session-at <uuid>`, with `--add-dir`; should that fork's init not list the folder or not carry that id, or the CLI refuse the combination, a fork starts with none and this line is revised); a new session with none; not across IDE restarts (2.2). A folder that no longer exists when a spawn is built is dropped, with the WARNING notice `The folder <path> no longer exists, so it was not added.`; checked on IO before the spawn.

### 3.5 Keyboard and focus (`ui-accessibility`)

- **Ring and popover.** The ring stays one focus stop (`Context window`, role button) with Enter and Space to open, Esc to close; focus returns to the ring when the popover closes. ## 7. Errors and edge cases

- **A CLI without `get_context_usage` or `get_usage`**: an error answer is shown verbatim (popover, card), or a timeout; no version gate: try, then show. The card's CLI text stays reachable either way.
- **A CLI that stops sending `id` on categories** (probes open question 8): rows still draw, grey, ordered by `kind`; without `kind` they sort last; never matched on `name`.
- **Mid-turn requests**: sent (nothing is gated on `busy`); a timeout shows as one; the turn-end refresh retries the popover by itself (3.1). `/usage` typed while Claude works is sent `later` only once D8's `queue-later-command` shows a `later` local command running as its own zero-turn turn after the running one (**unrecorded** until then, and refused while busy, 12.1, 12.2); then its fetch starts on that zero-turn `result`: its first `get_usage` goes out between turns, as the probes sent it (3.2), unless another queued message starts right after it. Two cases can still reach the CLI while a turn runs, neither recorded (11 item 2): a card's `Retry` (not gated on `busy`), and the 60 s scan still running when the user sends the next prompt. Each degrades to a timeout with `Retry`, so nothing fails silently.
- **The process ends mid-request**: `Reply.Ended` → `The session has ended.` in the card part; the popover turns to its stopped state (the controller watches `status`). A popover closed mid-request cancels its call; a late answer goes to the reducer (MCP 4.2): a success is ignored, an error shows as `The CLI rejected a request: …`.
- **Two `/usage` in one session**: each notice has its own `sourceUuid`, so answers land on their own card.
- **Huge lists**: groups draw at most 100 items (3.1); share rows and behaviours are not capped (the CLI sends a handful per kind).
- **Odd numbers**: `maxTokens` 0 or absent → shares `—`, no bar, header from the ring; `percentage` absent → computed from `totalTokens / maxTokens`, rounded, as `ContextFormat.value` does; a negative or non-numeric count skips the entry; `pct` outside 0..100 skips the entry.
- **`rawMaxTokens` below `maxTokens`** (**docs only**, a compaction window): the header still shows `maxTokens` and the CLI's `percentage` (whether the CLI divides by `rawMaxTokens` or `maxTokens` is unknown: every recording has both at 1000000, probes 2.1); revisit with a recording (11 item 4).
- **Plugin text**: names and descriptions are config text, drawn as plain `Text`, never Markdown; a version failing 4.1's check is not drawn. A command whose prefix names no listed plugin (a built-in's, or a plugin that failed to load) is not in any page once an init came; it stays in the palette. Before the first init, a catalogue name with a colon that is not a plugin's (none recorded) would show as a plugin until the init replaces the list.
- **Folders**: the folder is deleted after it was added → dropped at the next spawn with its notice;; the same folder through a symlink → one real path, `is already added`; a folder on another volume or a network share → passed as chosen after `toRealPath()`, whatever the CLI then says is shown (init comparison); the user removes a `PENDING` folder before any spawn → it simply leaves the list, and if the process was already stopped for it, the next prompt resumes without it.
- **A prompt queued while a respawn waits**: a message waiting in the CLI's queue (12) keeps the session busy, so the respawn for a folder waits until it has run; a prompt sent while the process is stopped for the respawn goes to the next spawn (`SessionHandle.sendOrQueue`), which already carries the folders; nothing is sent twice.
- **Fork**: a whole fork or a fork at a reply (13) copies the parent's folders and passes them as `--add-dir` after `--fork-session --session-id <new id>` (and `--resume-session-at <uuid>` for a fork at a reply) (D0 records that exact argv; if the CLI refuses it or the fork's init does not list the folder, a fork starts with none, 3.4); the fork's first init confirms them for the fork.
- **Markdown in `/context`'s notice**: the text is the CLI's report built from local data (paths, tool and skill names). It is rendered with the same renderer and the same rules as replies; nothing in it is executed.

- **Sending while Claude works** (12): the process ends with messages waiting → each returns with the WARNING notice; Stop → the cancelled ones, and any the receipt names in neither list, return with the INFO notice and those in `still_queued` stay; a refused withdraw → the INFO notice and the bubble back, or only the notice when the CLI started the message before it answered; a prompt sent while a `!` command runs → held behind that command's escape, and sent at once if the command sends nothing (12.4); a prompt sent while a context-only escape's quiet `result` is due → held until it (12.4); a busy draft with images, until D8's `queue-later-command` shows a `later` image message running → refused with its notice, the draft kept (12.1); a lifecycle line for an unknown uuid, or for the turn's own prompt (`interrupt:5,7,20`) → nothing; no lifecycle at all → the `result`'s `user_message_uuids` folds; a CLI without the capabilities → Enter refused with its notice; a CLI that ignores `priority` and folds a `later` message → it shows as folded, since the lifecycle decides; two `later` messages starting in one turn (unrecorded) → the second shows as folded into the first's turn; a queued turn's `init` with another model → the model check's notice, as for any turn; `queued_turn_count` is ignored.
- **A folded message on reload** (12.1): a `queued_command` on a sidechain or with a `commandMode` other than `prompt` is skipped; one without `source_uuid` uses the line's `uuid`; image blocks in its prompt become images (unrecorded).
- **Fork at a reply** (13): an unknown uuid → 13.1's error path, shown, and every respawn repeats it visibly; a turn whose last main-thread line is a `tool_use` forks there (accepted, **probe run**); a reply over several lines (thinking, then text: `permission-mode:30` and `:34`, one message `<id-28>` over the lines `<uuid-36>` and `<uuid-41>`) forks at its latest complete line, `<uuid-41>`; how such a message's lines chain in the transcript is unrecorded (no `transcripts/permission-mode.jsonl`; 11 item 14); a fork before a compaction boundary, a fork while the original's process is live, and a folded message inside the forked turn (copied as its `queued_command` line, then read as folded) are unrecorded (11 item 14).
- **Shift+Tab** (14): a refused mode is skipped until the CLI reports it or the process ends; key repeat steps one mode per repeat, each a `set_permission_mode` that the reducer chains; a stopped session records the pick for the next spawn, and a first `init` after a spawn that reports another mode than the `--permission-mode` passed gets 14.1's WARNING, unless a pick reached the live process before that `init` or the `init` has no `permissionMode`; an open footer menu, popover or `+` menu disables the action; Shift+Tab in the editor still unindents.
- **Orbs and shimmer** (15): `Reduce motion` toggled during a turn stops or restarts both at once (the orbs restart from their cycle's first frame, as in 0.1.2); the tool window hidden or the row scrolled away → no frames; a waiting or not-responding row neither moves nor shimmers.
- **The card's detail** (16): `total_cost_usd` 0 or absent → no share; a model without `costUSD` → none for it; more than three tips → the disclosure.

## 8. Performance

No request while the popover is closed; at most one `get_context_usage` in flight per session; one pair of `get_usage` per `/usage`. Payloads (a few KB; the probe's `full` answer carries a 200-cell `gridRows` that is skipped, not decoded) decode on `Default`; models build on `Default`; the popover's rows are at most the categories (about 15) plus the groups' first 100 items each, built only for expanded groups. The card is one row in the `LazyColumn`, keyed by the notice id, recomposed only when its part states change. The plugin pages are built from `ComposerModel`, which changes only when the init or the catalogue does. The folder checks and the init comparison run on `IO`. A folder change costs one respawn (MCP servers and plugins reconnect), only when the user adds or removes a folder. Sections 12 to 16: a message sent while Claude works is one frame, as a prompt is; a withdraw is one request; each waiting message is one row. The fork point is a field the reducer sets, so nothing is read until a fork is clicked. The mode cycle reads state under the handle's lock and never waits. The orbs (0.1.2, unchanged) redraw one square a line of text high, in a layer of their own, at most about 30 times a second while a turn runs and is shown; the shimmer adds an offscreen layer for 900 ms of every 3000 ms; neither runs while idle, hidden, off screen or under `Reduce motion` (15.2).

### 12.1 What the user sees

**Today.** While a turn runs the composer refuses Enter (`composerKey` maps Enter to `Send` only when not busy, and `composerFallback` swallows the rest) and shows Stop in place of Send (`PromptBox`). The session layer would already write a frame to a live process at once (`SessionHandle.sendOrQueue`). The CLI queues a `user` frame written mid-turn itself and never drops it, and reports it with `command_lifecycle` lines for the frame's `uuid`: `queued`, `started`, `completed` or `cancelled` (probes 5). So Tandem keeps no queue of its own: it writes each message at once and draws it from those lines. The one exception is a prompt behind a shell escape (12.4).

**Gate.** Messages can be sent while Claude works when the process's latest `system/init` lists both `msg_lifecycle_v1` and `interrupt_cancel_queued_v1` in `capabilities` (`queue-fold:6`, `queue-cancel:5`; also older fixtures, `plain-reply:4`, `interrupt:8`). Otherwise the composer behaves as today and says why (12.2).

**Keys**, in the composer's text area, while busy (a turn runs, or a message waits in the CLI's queue):

- **Enter** sends now, with no `priority`. The CLI takes it into the running turn at the next tool round: `queued` at once (`queue-fold:19`, after the Bash's `task_started` at `:18`), `started` right after the tool result (`:21`, `:22`), a `system/status` whose `user_message_uuids` lists [P, F] (`:23`), one `result` with `num_turns` 3, `user_message_uuid` P and `user_message_uuids` [P, F] (`:53`), the reply ending with F's request (`KIWI`). With no tool round left (F written while the final text streams), the CLI runs it as the next turn right after the `result` (**probe run**; D8 records it).
- **Ctrl+Enter** (**⌘↵** on macOS; both modifiers accepted on every OS) sends with `"priority":"later"`: never folded in, it waits for the running turn's `result` and starts as its own turn (`queue-later:19` queued; the `result` at `:51` names P only; `:53` F `started`, `:54` its `init`, `:63` its own `result`, `user_message_uuid` F). The SDK's own sends use it "so a running turn cannot reorder them" (its types; the field is typed there but undocumented in the public docs).
- **Idle**: Enter sends, as today; Ctrl/⌘+Enter also sends.
- **A draft with images**, while busy: never sent without `later`, so that Tandem never asks for an image to be folded into a running turn (folding one is **unrecorded**; the recorded image prompt, `user-image`, was sent while idle and ran as its own turn). When it shows the image message `queued`, then `started` (after the running turn's `result`, or folded into a turn still open) and the turn it ran in ending in a `result` without error, a busy draft with images is sent `later` whichever key, and should it fold, its lifecycle lines show it folded (7). Until then, and with any other outcome (an error, `cancelled`, or no `started`), it is refused while busy with 12.2's notice, the draft and its images kept, as a slash command is.
- **A slash command Tandem does not intercept** (MCP 3.4; `isSlashCommand`: a draft whose first word is `/<name>` with `<name>` in the palette's list, the catalogue's `commands` and `slashCommandNames` plus Tandem's own rows; a draft that merely starts with `/`, such as a path in `/src/app.kt fails to compile`, is a prompt), while busy: sent while idle, a local command such as `/usage` or `/context` runs as its own zero-turn turn (`parity-usage:22-23`, `parity-context:24-25`), but one sent with `priority:"later"` while a turn runs is **unrecorded**: the queue probe's only ground was the SDK's types, which say the SDK sends `/effort` that way. Were the CLI to run it at once or fold it, its `started` would fold into the open turn, the local-command notice (MCP 3.5) would mark the running model turn local, that turn would end with no footer and no `turnsEnded`, and a `/usage` card would fetch on the wrong `result`. D8's `queue-later-command` records it (during a Bash, `/context` with `later`). When it shows the command `queued`, then after the running turn's `result` its `started` and a zero-turn local `result`, such a command is sent `later` whichever key, and a palette pick that would send a command while busy (today `Ignored`, MCP 3.4) sends it `later`. Until then, and with any other outcome, it is refused while busy with 12.2's notice, the draft kept, and a busy palette pick stays `Ignored` with the same notice. The four intercepted commands (`/mcp`, `/model`, `/permissions`, `/mode`) still act at once, busy or not.

**The pending bubble.** A message waiting in the CLI's queue is not a chat entry: it is a `QueuedRow` drawn after the working row, in send order, a dimmed user bubble with its text and image thumbnails and a caption: `Sent · Claude reads it at its next step` (Enter while busy, a steer), `Queued · sends when Claude is done` (`later`), `Waits for the shell command's output to go out` (held behind a shell escape, 12.4), or `Withdrawing…` while a withdraw is out (12.3). Its state follows the CLI's lines for its `uuid`:

- `queued`: the bubble stays (`queue-fold:19`, `queue-later:19`).
- `started` while a turn is open: it was folded in. The bubble becomes a user bubble at that point of the turn, right after the tool result that ended the round (`queue-fold:21-22`; the transcript puts its `queued_command` line at the same place, `transcripts/queue-fold.jsonl:23`), with the caption `Sent while Claude worked` under it. The turn stays one turn with one `Worked for` footer (`queue-fold:53` is its only `result`).
- `started` with no turn open: a new turn. It becomes an ordinary user bubble and opens the turn (working row, busy), as a send does today (`queue-later:53`, after the `result` at `:51`).
- `completed`: nothing (`queue-fold:52`). `cancelled`: the bubble leaves (12.3; `queue-cancel:24`, `:55`).
- No lifecycle line at all (a CLI that stops sending them): a `result` whose `user_message_uuids` names a waiting `uuid` folds it in before that turn's footer (`queue-fold:53` names both).

The CLI never echoes a mid-turn message on stdout (no `user` line carries F in `queue-fold`), so the bubble's text and images are Tandem's own copy of what it sent.

**The composer.** Busy, with mid-turn sends on: the placeholder reads `↵ to send, ⌘↵ to queue for later` on macOS and `Enter to send, Ctrl+Enter to queue for later` elsewhere; Stop stays at the right, and once the draft can be sent a `Send` button (`↵`) appears to its left, tooltip `Send now · ⌘↵ queues it for after this turn` (`Send now · Ctrl+Enter queues it for after this turn` off macOS), a click acting as Enter. Busy without them: `Claude is working · Esc to stop`. Idle: `Type / for commands`, as today. The composer counts as busy while a turn runs or any message waits (`ComposerModel.busy = state.busy || state.pendingSends.isNotEmpty()`), so Stop and the hint hold still through the gap between a turn's `result` and the queued turn's `started` (`queue-later:51` → `:53`, about 10 ms in the probe run).

**Reload.** A folded message reaches the transcript only as an `attachment` line of type `queued_command`, `{"prompt":[{"type":"text","text":"Also say the word KIWI at the end."}],"source_uuid":<F>,"delivery_id":…,"commandMode":"prompt",…}` (`transcripts/queue-fold.jsonl:23`), then a `queue-operation` `remove` with `reason` `absorbed_mid_turn` (`:24`); no `user` line names it. Today's `TranscriptReader` skips every `attachment` line (`docs/protocol.md` 11), so the message vanishes when the session is reloaded (seen once with a temporary test, probes 5). New: the reader reads a `queued_command` attachment that is not on a sidechain and whose `commandMode` is absent or `prompt` as a folded prompt, `UserSent(folded = true)`, with `source_uuid` (else the line's `uuid`), the text of its string or text blocks, its `image` blocks as images (**unrecorded**) and its timestamp; it lands where the live bubble did. A `later` message is an ordinary `user` line on disk (`transcripts/queue-later.jsonl:32`, `parentUuid` the last assistant line) and already reloads. A withdrawn message leaves no `user` line (`transcripts/queue-cancel.jsonl`: `enqueue` and `dequeue` at 19-20 for F1; `enqueue` and `remove` with `reason` `cleared_on_cancel` at 33-34 for F2), so a reload shows neither, as neither ran.

### 12.3 Withdrawing a message, and Stop

**Edit and Cancel.** A `later` message's bubble has two icon buttons: `Edit queued message` puts its text and images back in the composer (ahead of any draft) and `Cancel queued message` discards it. Both send `{"subtype":"cancel_async_message","message_uuid":<uuid>}` (5 s). Recorded: the CLI closes the message with lifecycle `cancelled`, answers `{"cancelled":true}`, the running turn goes on as if nothing had been sent, and the message never runs (`queue-cancel:23-25`, then `:36` the turn's `result`, `DONE`, and nothing more for F1). The bubble reads `Withdrawing…`, its buttons disabled, until then. An answer `{"cancelled":false}` (the SDK's types say so for a message already taken; **unrecorded**), an error or a timeout puts the bubble back and adds the INFO notice `Claude had already taken "<first line>"; it was not withdrawn.`; it then folds or runs as the CLI decides, which shows. When the CLI started the message before it answered (its `started`, or a `result` naming it, came first), there is no bubble to put back, since the message already shows as sent: only the notice is added, its text kept from the withdraw. A message held behind a shell escape (12.4) is withdrawn locally, with no frame.

**A steer's bubble** (a message sent with Enter, no `priority`) has no Edit or Cancel this round: `cancel_async_message` is recorded only for a `later` message. D8 records it for a steer before its tool round ends; if that recording answers `{"cancelled":true}` and the message never runs, the steer's bubble gets both buttons and this paragraph says so; otherwise it stays without them (2.2) and Stop is its way out.

**Stop** (the button or Esc) stops everything, as the SDK's types advise for a Stop button. When a message waits in the CLI's queue and the init listed `interrupt_cancel_queued_v1`, the `interrupt` carries `"cancel_queued":true`. Recorded for a `later` message: the CLI closes it with lifecycle `cancelled` and lists it in the receipt's `cancelled` before the aborted turn's `result` (`queue-cancel:55`; `:56` `{"still_queued":[],"cancelled":[<F2>]}`; `:60` `error_during_execution`, `terminal_reason` `aborted_tools`; `:61` P2 `cancelled`; no further `init`), and the message never runs; for a steer it is **unrecorded** (D8). Each cancelled message goes back to the composer, text and images, ahead of the draft, with the INFO notice `Not sent: "<first line>". It is back in the composer.`; messages held behind a shell escape are dropped and returned the same way. A message the receipt lists in `still_queued` instead stays a bubble and runs after the stop, as the CLI decides. A message still waiting when the receipt arrives that neither list names, and that no lifecycle line has closed, is no longer held by the CLI and no later line would clear it: it goes back to the composer with the same INFO notice, so Stop always clears what waits (CLAUDE.md: validate everything that comes from the CLI). Without the capability, `interrupt` is today's frame and a `later` message survives the stop and runs; its bubble stays. With nothing waiting, `interrupt` is today's frame byte for byte, so `interrupt`, `history-interrupt` and their tests do not change. Tandem never resends anything by itself: a message written after a stop makes the model redo the stopped request along with the new one (**probe run**). `priority:"now"` is not used (2.2).

### 12.4 Images, slash commands and bash mode's held frames

- **Images** go `later` (12.1), with the caption `Queued · sends when Claude is done`, and so do **slash commands not intercepted**, each only with its D8 outcome for `queue-later-command` (**runs** for the image message, **after the turn** for the command); otherwise each is refused while busy (12.1, 12.2).
- **`!` while busy** (a turn runs, a message waits, or a `!` command runs): not run, and the draft stays in the composer (today `runShell` ignores a second command and the draft is cleared); the composer notice `Shell commands run when Claude is done: wait for the reply, or press Esc to stop.` (MCP 12.6 swallowed it silently).
- **Held frames.** `ClaudeSession` already holds a shell escape whole while a turn is open (`heldEscapes`) and holds a responding escape's output frame until the quiet `result` of its command frame (`pendingOutput`), because the CLI merges sends queued before it starts processing (`bash-mode:3-6`, MCP 12.4). Two rules join them. (1) A held escape starts only when no turn is open **and** no message waits in the CLI's queue: a `later` message starts about 10 ms after the running turn's `result` (`queue-later:51` → `:53`) and would race the escape's quiet frame; the escape goes after every message already queued, its row showing its sending state until then. (2) A prompt sent while a `!` command runs, while escapes are held, while an output frame waits for its quiet `result`, or while a quiet send's zero-turn `result` is still due (`quietSends` not empty: a context-only escape's frame) is held in `ClaudeSession` in send order (stage `HELD`, caption `Waits for the shell command's output to go out`), whether or not the init listed the capabilities (no CLI queue is involved, so a running `!` alone never makes Enter refuse), and written once the escape's last frame has gone out and every quiet `result` has come back, with its own priority. A running command holds its place in that order from its start (`ShellStarted`), because its escape reaches `ClaudeSession` only after it has ended (`SessionManager.runShell` dispatches `ShellEnded`, then sends the escape): the escape takes the command's place, so a prompt sent while the command ran goes out after the escape's frames; a command that ends without sending anything (not started, failed, killed at the IDE's exit) gives its place up, so the prompts behind it go out at once, never held with nothing to release them. A process attached while a `!` runs starts with that command's place. This keeps MCP 12.4's rule that an escape never goes out right behind a prompt, stops a steer overtaking an output frame, which would break the turn tracking, and never writes a prompt right behind a quiet frame, so the unrecorded quiet-plus-querying batch of MCP 12.9 item 7 cannot happen: it closes that item ("a prompt is not held") by holding while `pendingOutput`, `heldEscapes` or `quietSends` is not empty, as the item proposed.

### 12.5 Never silent, and what counts as idle

- **The process ends** with messages that never started: each goes back to the composer with the WARNING notice `Not sent: "<first line>": the CLI ended before reading it. It is back in the composer.`
- **The session is stopped or closed** (`SessionHandle.stop`, `settled()`): waiting messages go back with Stop's INFO notice.
- **A fork** (the sidebar's whole fork or `Fork from here`) builds its history with `forkHistory()`: `settled()` without the waiting and returned messages and without their `Not sent` notice. A message waiting in the original stays the original's and still runs there; the fork's composer gets nothing back.
- **A refused withdraw** and **a missing capability** say so (12.3, 12.2).
- **Every queued turn's `init`** runs the model check, as every `init` does (`queue-later:54`).
- **`result.queued_turn_count`** is 0 even with a `later` message waiting (`queue-later:51`), so it is never read as a turn-over signal.
- **Attention and the IDE notification** on a turn's end wait while any message waits, so a queued turn does not raise them twice; they come after the last queued turn ends.
- **Idle**: the session counts as `RUNNING`, not idle, while any message waits: no eviction by the live-session cap and no respawn for a folder (3.4) until it has run.
- `<first line>` is the message's first line, cut at 60 characters with `…`; logs name uuids and stages only (CLAUDE.md "never log prompt contents").

### 13.1 What the user sees

**Today.** `Fork from here` is enabled on the latest ended turn's reply only (`ForkState.NOT_LATEST`: `Only the latest reply can be forked`) and forks the whole session (`SessionManager.fork(id)`: `--resume <id> --fork-session --session-id <new id>`, fixture `fork`). New: every ended turn's reply has it, and the fork's history ends with that turn.

**Which uuid.** A reply forks at one uuid: the latest complete line of its turn's last main-thread assistant message (`parentToolUseId == null`), kept as `ChatEntry.Assistant.lastUuid`, which the reducer sets on every complete assistant line, live or reloaded. The stream's and the transcript's uuids are the same (`<uuid-14>` on `fork-at:11` and on `transcripts/fork-at-origin.jsonl:20`), so the fork point is known without reading the file again. For a turn that ended normally it is the reply's last line, a clean cut: the fork answers `ALPHA` only (`fork-at:65`). A turn stopped during a tool may end on a `tool_use` line; the CLI accepts it and reports no error (**probe run**). Never a user line: the CLI keeps that unanswered prompt and the model answers it again, tool calls included (**probe run**); the CLI also accepts an attachment line after the reply, which cuts the same way, but Tandem does not need it. Never a subagent line (not measured). A turn with no main-thread assistant line carrying a uuid has no fork point. The fork point lives on the row (`MessageActions.forkAt`), so a frozen turn keeps it, and a turn whose reply is only a notice (a local command, MCP 3.5) has no reply row and no button. User bubbles carry no `Fork from here`: a prompt's uuid as the cut makes the CLI run that prompt again (**probe run**, above), and a fork "before this prompt" is the fork at the reply above it, which already has the button (the first prompt has no reply above it: a fork there is a new session).

**The argv.** `--resume <A> --fork-session --session-id <B> --resume-session-at <uuid>` (the probe's order; `fork-at:57-70` is that process: its `initialize` answer at `:57`, its `init` with B at `:60`, `ALPHA` at `:65`, a `success` at `:70`), then `--add-dir <dir>` per added folder (3.4). Once the fork's own transcript exists it resumes as `--resume <B>`, as a whole fork does today. `SessionConfig` refuses `resumeSessionAt` without `forkSession`: without it the CLI does not truncate the original but appends a branch to `<A>.jsonl` whose new prompt's parent is that line, and a later plain `--resume <A>` follows the newest branch, which drops the turns after the cut from A's history (**probe run**). It also refuses a blank value or one starting with `-` (an argument, never a flag). There is no strict UUID check, since the fixtures and IDE tests use placeholders (`<uuid-14>`, `a1`); the guard is that `fork()` finds the uuid in the session's own history, so Tandem passes only a uuid its CLI wrote. A fork that has no transcript of its own yet (no prompt sent) shows A's lines with A's uuids, so forking it forks A: `--resume <A> --fork-session --session-id <C> --resume-session-at <uuid>`. The fork's first message gets a fresh uuid (`UUID.randomUUID`, as every send): the CLI leaves out of the fork's transcript a `user` message whose uuid repeats one in the copied history, although its turn runs (**probe run**).

**The original stays as it is.** `<A>.jsonl` was byte-identical after six fork runs, the failing ones included (**probe run**). After a close or an IDE restart: read from the fork's own transcript, whose copied lines keep their uuids, so the same replies come back with valid fork points. **A live original.** A fork usually starts from a session whose process is still open and idle; the committed `fork-at` forked after the origin had exited, so D8's `fork-at-live` records the live case. Should it show the CLI refusing, or a fork transcript unlike `fork-at.jsonl`'s, a fork at a reply first stops the original's idle process (`SessionHandle.stopIfIdle`, the cap's stop, which loses nothing: `docs/design.md` "Key choices") and then forks, so the button stays `ENABLED` on every ended turn's reply and `WAIT` stays only while a turn runs or a message waits. A turn that starts between the click and the stop makes the stop refuse: nothing forks, the chat says `Wait for the reply to finish` (13.2's `Refused.BUSY`), and the button reads `WAIT`. Disabling the button whenever the original has a live process would disable it on every reply of the session the user is working in, the over-promise the owner objected to.

**The error path.** A uuid the CLI cannot find, or a value that is not a uuid: exit code 1 before any `initialize` answer, one stdout line `{"type":"result","subtype":"error_during_execution","is_error":true,"num_turns":0,"errors":["No message found with message.uuid of: <uuid>"]}`, the same text on stderr, and no fork transcript (**probe run**; not a fixture, since a run with no `init` leaves no transcript to pair, as the fork probe noted). It shows in the fork's chat through today's paths, never silently: the `result`'s error notice with the CLI's `errors` text, and `The claude CLI exited with code 1.` with the stderr tail. A prompt sent then respawns with the same argv and fails the same way, visibly; the user can delete the fork. Tandem never falls back to a whole fork. An invalid `--session-id` exits 1 with `Error: Invalid session ID. Must be a valid UUID.` on stderr (**probe run**); Tandem's ids are `UUID.randomUUID`.

**Added folders** (3.4). A fork copies its parent's folders and passes them after the fork tail; a fork of a fork without a transcript copies that fork's folders. D0 records this argv with `--add-dir` (10); until then a fork at a reply carries folders on the same terms as a whole fork (3.4 "Lifetime").

## 14. Shift+Tab cycles the permission mode

Inputs: the owner's words, "I want a keybind to change modes while in a chat"; the keybinding diagnosis of the owner's second test (the CLI docs on permission modes and interactive mode, the IU 2026.1.5 jars and keymaps, the code at `522c3e2`, with `PromptBar`'s bash-mode `busy` at `604574b`; nothing was run); `chat/Modes.kt`, `session/SessionSpawner.OFFERED_MODES`, `ui/FooterControls.ModeControl`, `ui/ComposerKeys.kt`, `ui/PromptBar.kt` (`provideData`, `PASTE_PROVIDER`), `Reducer.rejectModeChange`; chat-redesign 4.18 (the keyboard map).

### 14.1 What the user sees

**Today.** The mode changes only through the footer's mode menu (digits 1-4, in the order Auto, Manual, Accept edits, Plan, `OFFERED_MODES`) and `/permissions` or `/mode`; there is no shortcut, and `plugin.xml` registers no action. The CLI cycles with Shift+Tab: Manual (`default`) → Accept edits → Plan, then Auto when it is available, with no confirmation; from Auto the next press goes to Manual; bypass only when the process was launched with it; dontAsk never (CLI docs).

**The action.** `Tandem.CyclePermissionMode`, text `Cycle Permission Mode`, description `Switch the Tandem chat to the next permission mode: Manual, Accept edits, Plan, then Auto when the model supports it`, default shortcut Shift+Tab in `$default` (the macOS keymaps inherit it), rebindable under Settings | Keymap | Plugins | Tandem and listed by Find Action. It is enabled only when the data context holds `COMPOSER_MODES`, which the composer's text area provides (Jewel `provideData`, beside its paste provider) while it holds the focus and none of the footer menus, the ring's popover or the `+` menu is open (each counts itself in `ChatUiState.openMenus` while open, 14.3). So it acts only in the composer; in the editor, dialogs, the sidebar, cards and the footer, the platform's own Shift+Tab actions (six in `$default`, each enabled only in its own context) or focus traversal run as before. Keymap actions run before Compose's key handlers (the IDE's Paste takes Ctrl/⌘+V before Compose sees it, which is why `PromptBar` provides `PASTE_PROVIDER`), so the composer never sees the Shift+Tab the action took (read from bytecode, 11 item 15). `actionPerformed` runs on the EDT and only takes the handle's lock and queues a frame (hard rule 1); the action is `DumbAware` with `ActionUpdateThread.BGT`, and `update` only checks for the key. The slash palette stays open across it.

**Order.** `Modes.CYCLE = [DEFAULT, ACCEPT_EDITS, PLAN, AUTO]`, the CLI's order (not the menu's). `Modes.next(current, autoSupported, rejected)` walks it from the current mode, wrapping, and returns the first allowed mode: `AUTO` only when the shown model `supportsAutoMode`, never a mode in `rejected`. Start positions: a mode in the cycle starts at itself; `BYPASS_PERMISSIONS` at Plan's slot (→ Auto, else Manual), the CLI's slot for it; `DONT_ASK` at Auto's (→ Manual); no mode yet counts as Manual, the CLI's own start, so the first press asks for Accept edits; the fallback is Manual. Tandem never cycles into bypass or dontAsk (neither is in `OFFERED_MODES`).

**No stale reads.** `SessionManager.cyclePermissionMode(id, Modes::cycleFrom)` calls `SessionHandle.pickMode(next)`, which reads, under the handle's lock, the live process's own state (it already holds every earlier pick, synchronously), else the handle's, computes the next mode and picks it through today's path (`PermissionModeRequested`, then `set_permission_mode`). Quick presses and key repeat step one mode each (Manual → Accept edits → Plan); the composer model, followed on `Default`, could be one step old and send the same mode twice. The pick is also stored as `lastPermissionMode` for new sessions, as a menu pick is.

**Refused, stopped, busy.** The label changes at once (today's optimistic state) and then follows the CLI's `system/status`. A refusal reverts it with today's ERROR notice (`Reducer.rejectModeChange`; fixture `permission-mode-rejected`). New: the refused mode joins `ChatState.rejectedPermissionModes`, which `next` skips for the rest of the process (cleared when the process ends; a mode leaves the set when the CLI reports it in a `status` or an `init`), so Plan → Auto (refused) → back to Plan cannot hold a keyboard user in Plan. A stopped session records the pick, and the next spawn passes `--permission-mode`, as today. New: when the CLI starts in another mode than the one passed (after a respawn with `--permission-mode auto` where Auto is not available, the CLI starts in Manual), the first `init` after the spawn no longer overwrites the shown mode in silence: the chat gets the WARNING `The CLI started in permission mode <mode>, not <mode> as picked.` (wire names, as the rejection notice has them; hard rule 5). The check covers the spawn's own `--permission-mode` only: a pick made on the live process before that first `init` (Shift+Tab or the menu in a fresh or resumed chat, the key's natural first use) reaches the CLI as `set_permission_mode`, whose answer already reports a refusal (`rejectModeChange`), so the pick cancels the check; an `init` without `permissionMode` says nothing. The keybinding diagnosis found this gap for menu picks too; Shift+Tab makes it one key press away, and `rejectedPermissionModes` does not help a stopped session, since it is cleared when the process ends. A running turn or an open card does not block the cycle, as a menu pick is not blocked; the card is answered with its own controls (the CLI's other Shift+Tab meaning on a permission prompt, allow for the session, is not copied). A successful switch gets no chat notice, as in the CLI.

**Discoverable.** The mode menu's header row reads `Mode` and, dimmed at its end, the action's first shortcut followed by ` to cycle` (`⇧⇥ to cycle` on macOS; `KeymapUtil.getFirstKeyboardShortcutText`), left out when the action has no shortcut, so it follows a rebinding. A screen reader hears `Permission mode <label>` (`AccessibleAnnouncerUtil.announce`), since the change happens in the footer, outside the focused component.

### 14.2 Focus traversal (`ui-accessibility`)

Today plain Tab in the composer types a tab character (the bundled Compose maps an unmodified Tab to `KeyCommand.TAB` in a multi-line field; read from its bytecode, not run), so Shift+Tab is the composer's only keyboard exit inside the tool window, against chat-redesign 4.18; `ComposerKeysTest` asserts `assertNull(composer(tab))` with the comment "Shift+Tab (focus traversal)". Taking Shift+Tab alone would make the composer a keyboard trap (WCAG 2.1.2), so two changes ship together:

- **Tab moves forward.** Unmodified Tab in the text area moves the focus to the next control (`ComposerAction.FocusNext`, `moveFocus(FocusDirection.Next)`): Send or Stop, the mode, the model, the ring, then round the tool window to the header, the sidebar, the cards and the rows, as 4.18 says; an open palette's Tab still inserts the selected command (MCP 3.4). Typed tabs end; pasted ones still land.
- **Backward traversal stays reachable.** From every control outside the text area Shift+Tab is ordinary backward traversal, since the action is disabled there (the sidebar's Shift+Tab IDE test is unaffected); from the text area, Tab reaches every control round the cycle; Esc with nothing to close is left unconsumed, so the IDE's tool-window Escape can move to the editor (to check in `runIde`); and removing or rebinding the shortcut gives Shift+Tab back to backward traversal in the text area. The menu header's hint makes the binding discoverable.

### 15.2 Costing nothing when idle

- **No running turn**: no working row, so no orbs and no shimmer; a finished thinking row (`Thought for Ns`) is static.
