## 1. Goal

Claude changes files in the project, and every change lands the way a JetBrains user expects: through the IDE's `Document`, as one undoable command with local history, after a native side-by-side diff in which the proposal is editable. The user reviews Claude's edit, fixes it by hand where it is nearly right, and presses Accept (Ctrl+S, ⌘S on macOS): the final text, hand changes included, goes into the file, the file is saved to disk, and the tool result carries **the file as it now is** (the owner's "when I click save it will send the latest version of the file to the llm"), so the model's picture of the file is the file. **Accept is the owner's "save"**: there is no separate Save button because Accept does what Save does (the write command, then `FileDocumentManager.saveDocument`), and the IDE's Save shortcut inside the diff is bound to it (3.2). The rule for what goes back (4.3): the whole file, numbered, on every Accept while the file has at most 2000 lines and 64 KB; past that bound the edited region with its line numbers and `Read <path> for the rest.`, since a file that size would cost more context than it tells. Reject sends the model an error with the user's reason, and the turn goes on. In `acceptEdits` and `bypassPermissions`, or after `Accept all`, edits apply without a diff. The tools are Tandem's own, served to the CLI over the control channel it already has: no port, no Node, no sidecar (hard rule 2), no credentials (hard rule 3), nothing on the EDT but the IDE's own write action (hard rule 1), every failure in the chat (hard rule 5), a fixture test for every new frame (hard rule 6), and no "Claude Code" in a string (hard rule 8). The editor's selection and `@file` mentions reach the model as context (section 3.5).

## 2. Simplest working version, and what is deferred

### 2.1 This round

1. **Two tools, one in-process MCP server** (4.1): `edit_file` (the CLI's `Edit`: `file_path`, `old_string`, `new_string`, `replace_all`) and `write_file` (its `Write`: `file_path`, `content`), served as the SDK server `tandem` that `initialize` registers with `sdkMcpServers:["tandem"]` and the CLI drives with `mcp_message` control requests (probes 1.1). The built-in `Edit`, `Write`, `MultiEdit`, `NotebookEdit` stay disallowed.
2. **The editable diff** (3.1, 3.2): every `edit_file` and `write_file` call opens the platform's diff, the file's own `Document` read-only on the left, the proposal editable on the right, with `Accept` (Ctrl+S / ⌘S, Ctrl+Enter / ⌘↵), `Accept all`, `Reject` and a reason field under the editors. Accept applies the right side's text with `WriteCommandAction` and saves the document to disk; the result carries the file's current text (bounded), and the user's changes to the proposal when there are any (4.3).
3. **Auto-accept** (3.3): `acceptEdits`, `bypassPermissions`, or `Accept all` for the rest of the turn.
4. **One diff at a time** (3.4): pending edits queue in the order they arrived, across the project's sessions; each row says where it is.
5. **Every file case named** (section 7): not open in an editor, new file, the old string no longer matches, outside the project, read-only, too large, binary, a directory, an unknown tool, a CLI that does not take the server, Stop while a diff is open.
6. **Context** (3.5): `@` in the composer opens a file picker that inserts the CLI's own `@path` mention (which the CLI expands itself, probes 3); a file with unsaved changes is sent from the editor's buffer instead; the active editor's selection goes with the prompt as a chip the user can remove.

### 2.2 Deferred (with the reason)

- **A `read_file` tool that sees unsaved buffers.** The model reaches for the built-in `Read` (not deferred, in every prompt it was trained on); a second read tool would be used rarely and would still race the disk. Instead, every `edit_file` matches against the editor's `Document` (the buffer, unsaved changes included), and a miss returns that text (4.3), so the loop converges in one extra round; `@path` of a dirty file sends the buffer (3.5). A `read_file` tool, and `NotebookEdit`'s equivalent, wait for a case the owner hits (11 item 1).
- **`multi_edit`.** The CLI itself dropped `MultiEdit` (`docs/protocol.md` 1.1: in no 2.1.302 `init.tools`); several `edit_file` calls each get their diff, in order (3.4).
- **The http/sse server with `--mcp-config`.** The control channel needs no port and was recorded working; the alternative was not tried (probes 1.1).
- **`sdkMcpServerManifests`** (**binary**: a one-shot cache of the handshake that lets the CLI skip `tools/list`) and **`sdkMcpServerConfigs`** (per-tool `always_ask` / `always_deny`): the live handshake is three frames and the permission request arrives in every mode anyway (probes 1.2); neither is sent (11 item 3).
- **Lifting the deferral.** The tools are deferred like every MCP tool: the model calls `ToolSearch` first (`r1:19`, `:21`). Nothing recorded lifts it; not attempted (11 item 4).
- **The CLI's own IDE integration** (**binary**: the `~/.claude/ide/<port>.lock` file with `authToken`, `--ide`, the `openDiff` / `FILE_SAVED` / `DIFF_REJECTED` flow, `at_mentioned` and `selection_changed` notifications, `ide_selection` / `ide_opened_file` reminders): a WebSocket server on a port and a lock file in the user's config directory, with the file written by the CLI from the IDE's returned text rather than through the `Document`, and whether the CLI connects to it in stream-json mode is unrecorded. Tandem's own tools and context blocks cover the same ground without a port (11 item 5).
- **The read-before-edit rule** of the CLI's `Edit` ("File has not been read yet"): the diff is the gate; the model edits what it has not read at the price of a mismatch error (4.3). Tandem does not track reads.
- **A diff for `write_file` of an existing file as a merge**, **per-hunk accept in the diff**, **opening the diff beside the chat instead of the editor area**: the two-sided editable diff is the simplest form of the owner's request; the IDE's own "Open diff as editor tab" preference is honoured (3.1) and nothing more.
- **Mentions of directories, of paths with spaces, during a running turn** (3.5): unrecorded (probes 3); the picker lists files only, and a mention is inserted as typed.
- **Edits from a subagent** (`parent_tool_use_id` set): the row nests under the `Agent` row as every subagent tool does; the diff opens the same way. No recording has one (11 item 8).
- **A setting to turn the tools off**, **a global "never show diffs" setting**: the mode menu's `acceptEdits` and the diff's `Accept all` are the two auto-accept choices; a user who wants no edits at all picks `plan` or tells Claude. No new setting this round (3.6).

## 3. What the user sees

### 3.1 The diff

**Opening.** When a `tools/call` for `edit_file` or `write_file` arrives and auto-accept (3.3) is off, Tandem opens the IDE's diff: `DiffContentFactory.getInstance().create(project, document, virtualFile)` on the left (the file's own `Document`, so unsaved changes show as they are) and `createEditable(project, proposedText, fileType)` on the right, in a `SimpleDiffRequest(title, left, right, leftTitle, rightTitle)` with `DiffUserDataKeys.FORCE_READ_ONLY_CONTENTS = [true, false]` (the left side cannot be typed into; the right can), `PREFERRED_FOCUS_SIDE = Side.RIGHT`, `DiffUserDataKeysEx.BOTTOM_PANEL` = the bar of 3.2, `DO_NOT_CHANGE_WINDOW_TITLE = true` (probes 2 has every signature; `DiffUserDataKeysEx`, `DiffEditorTabFilesManager`, `ChainDiffVirtualFile` and `DiffUtil` live in `intellij.platform.diff.impl.jar`, the rest in `intellij.platform.diff.jar`, **javap**). It is shown through `DiffEditorTabFilesManager.getInstance(project).showDiffFile(ChainDiffVirtualFile(SimpleDiffRequestChain(request), title), true)`, which returns the `FileEditor[]` that holds it, so the IDE's own preference decides between an editor tab and a window (Settings | Editor | General | Editor Tabs, "Open diff as editor tab"); the tab or window is focused. For a new file (`write_file` of a path that does not exist) the left side is `createEmpty()`. At open time Tandem also creates a `RangeMarker` on the file's `Document` for each matched range (`Document.createRangeMarker(start, end)`), so the ranges follow the file while the diff is open (3.2, Accept).

Strings: window and tab title `Tandem: <file name>`; left title `Current` (with `Current (unsaved changes)` when `FileDocumentManager.isDocumentUnsaved(document)`); right title `Proposed by Claude`. For a new file the left title is `New file`.

**The right side is a real editor**: syntax highlighting from the file's type, the IDE's completion is off (it is an in-memory document), undo within the diff works as in any editor. The user changes the proposal there as they like: the diff re-computes as they type, as the platform does.

**Closing without a choice** (the window's ×, the tab's close, Esc in the diff) counts as `Reject` with no reason (3.2). The IDE's "close all tabs" does the same. Tandem learns of it from the diff's **file editor going away**, not from `DiffRequest.onAssigned(false)`: `DiffRequestProcessor` calls `onAssigned(false)` and then `onAssigned(true)` on the same request every time it re-applies it (**javap**: `doApplyRequest`'s lambdas, run when the user switches the viewer side-by-side ↔ unified, or the processor refreshes), so a viewer switch would read as a close. Instead, `Disposer.register(editors[0], …)` on the `FileEditor` that `showDiffFile` returned (a `FileEditor` is `Disposable`, disposed when its tab or window closes, in either placement) resolves `Rejected(null)` when no choice was made, and a `FileEditorManagerListener.fileClosed` (`FILE_EDITOR_MANAGER` on the project's message bus, filtered on the `ChainDiffVirtualFile`) is the belt for a close the disposal misses. `onAssigned` is not used for closing.

**Several files**: each call is one diff; see 3.4.

### 3.2 The bar under the diff, and what each button does

A panel (`DiffUserDataKeysEx.BOTTOM_PANEL`) with, left to right: the text `Claude proposes an edit to <file name>. Change the right side as you like, then accept or reject.` on the first line; on the second a text field with the placeholder `Reason (optional): goes back to Claude with a rejection` that takes one line, then the buttons `Accept` (the default button; tooltip `Apply the right side to <file name> and tell Claude (Ctrl+S)`, `⌘S` on macOS), `Accept all` (tooltip `Accept this and every other edit Claude makes in this turn without a diff`) and `Reject` (tooltip `Change nothing and tell Claude why (Esc)`). The buttons are `JButton`s on a `DialogWrapper`-free panel; `Accept` is bound to the shortcuts of the IDE's `SaveAll` action (read from `ActionManager.getInstance().getAction("SaveAll").shortcutSet`, Ctrl+S or ⌘S by default) and to Ctrl+Enter / ⌘↵, both registered with `DiffUtil.registerAction` (probes 2) on the component of the `FileEditor` that `showDiffFile` returned (`editors[0].component`, which contains the right side's editor: a shortcut registered there wins over the keymap's `SaveAll` while focus is inside it) and on the bottom panel, before focus moves to the right side, so Save inside the diff is Accept and never the IDE's Save All; outside the diff the IDE's Save All is untouched. `Reject` is bound to Esc on the same components.

**Accept.** The right document's text is read on the EDT, then applied to the file's `Document` in one `WriteCommandAction` named `Tandem: edit <file name>` (`Tandem: create <file name>` for a new file), so Ctrl+Z in the editor undoes the whole edit and Local History shows one entry under that name. The left side is the live `Document`, which may have changed while the diff was open (the user typed in the file, another accepted edit landed, an IDE reformat ran), so **inside the write command Tandem checks the file first**: for `edit_file` with the proposal unchanged, the ranges are taken from the `RangeMarker`s made at open time (3.1); each must still be valid and its text must still equal `old_string`, else `EditMatcher.match` is re-run against the document's current text, and only a `Found` with the same count applies, from the last range to the first (`replaceString`, which keeps the caret and folds of an open editor); for a changed proposal, and for `write_file`, the document's current text must still equal the `original` the diff showed, and then the whole document is set to the final text (`setText`). On a mismatch nothing is written: the diff closes, the reply is the `The file changed while the diff was open` error of 4.3 with the document's current text, and the notice `Could not apply the edit to <file>: the file changed while the diff was open` shows (hard rule 5); the model retries against the text it was given. After the write command, **still on the EDT, Tandem saves the document to disk**: `FileDocumentManager.getInstance().saveDocument(document)` (`intellij.platform.core.jar`, **javap**). The owner's "when I click save" means the file is saved: the model's next `Read`, `Grep`, `Bash` (`./gradlew test`) and the CLI's own `@path` expansion all read the disk, so without the save every follow-up tool of the same turn would see the pre-edit file while the result said the edit landed. A save failure (an `IOException`, a refused write) is the "IDE refused" error of 4.3 plus the notice `Could not apply the edit to <file>: <reason>`; the edit stays in the buffer, undoable. A new file is created on disk (`VfsUtil.createDirectories`, `createChildData`) because a `Document` needs a `VirtualFile`, with its content set in the same command and saved the same way. Then the diff closes and the tool result of 4.3 goes to the CLI: the `mcp_response` goes out only after the save returned.

**Accept all.** As Accept, and the session enters `Accept all` for the rest of this turn: every later `edit_file` / `write_file` call of this turn applies without a diff (3.3). The turn's `result` line ends it; the next turn's edits show diffs again.

**Reject.** The diff closes, nothing is changed, and the tool result is an error carrying the reason when one was typed (4.3). The turn goes on: the model reads the reason and answers or tries something else (`r1:95`, `:108`).

**A diff left open.** Claude waits (the CLI holds the `tools/call` until the host answers, probes 1.4). The chat row says so (3.4) and `Stop` withdraws it (7.11). The CLI's own per-call timeout (`MCP_TOOL_TIMEOUT`, **binary**, default unmeasured) may cancel a diff left open for very long: Tandem treats that cancellation as 7.11 and the row says `Claude stopped waiting for this edit.`

### 3.3 Auto-accept

An edit applies without a diff, with the same `WriteCommandAction`, the same save to disk (3.2) and a result that says so, when either of these holds at the moment the `tools/call` arrives:

- the session's permission mode is `acceptEdits` or `bypassPermissions` (`ChatState.permissionMode`, the mode the CLI confirmed: `system/init.permissionMode` or `system/status` after `set_permission_mode`, `docs/protocol.md` 4.4). The CLI still sends `can_use_tool` for Tandem's tools in those modes (`r2:66` under `acceptEdits`, `server_policy_ask_only:true`): Tandem answers `allow` and skips the diff itself;
- `Accept all` was pressed in a diff of this turn (3.2), until the turn's `result`. `Accept all` is per session and per turn, not per file.

`auto` mode shows the diff (the CLI's classifier decides nothing about Tandem's tools; the request arrives as in `default`). `plan` mode applies nothing: see 7.9. `dontAsk`: the CLI denies ask-policy calls itself; no `tools/call` arrives (**docs only**, the binary's `always_ask` text).

The row of an auto-accepted edit reads `Edited <file>` with the tag `auto-accepted` (3.4), and the file's editor, if open, shows the change at once; the user undoes it with Ctrl+Z as any edit.

### 3.4 The chat rows and the queue

`mcp__tandem__edit_file` is `ToolKind.EDIT` (`ToolKinds.tandemTools` already maps the prefix `mcp__tandem__edit`) and `mcp__tandem__write_file` is `ToolKind.CREATE` (new prefix `mcp__tandem__write`). Labels follow `ToolLabels.fileForms` with the file name relative to the project: `Editing <file>` / `Edited <file>` / `Failed to edit <file>` / `Rejected edit of <file>`, and `Creating <file>` / `Created <file>` / `Failed to create <file>` / `Rejected creating <file>`. The row's body is the result's text in the editor font (`ToolBody.Mono`, as a `Write` without a patch shows today) and its `DiffStats` are counted from the input (`old_string` / `new_string` lines, or `content`'s lines for a new file) until a result gives better numbers.

New states while the call waits for the user, from `ChatState.edits` (4.4):

| `EditReview.phase` | Row label | Row action |
|---|---|---|
| `QUEUED` (another diff is open) | `Edit of <file> waits for the open diff` | none |
| `OPEN` | `Reviewing <file> in the diff` with a soft pulse of the orbs as a running tool has | `Show diff` (focuses the diff's tab or window) |
| after Accept with changes | `Edited <file>` + tag `with your changes` | none |
| after Accept, Accept all, auto | `Edited <file>` (+ tag `auto-accepted` when 3.3 applied) | none |
| after Reject | `Rejected edit of <file>` (`ToolState.DENIED`: the result's text starts with `The user rejected this edit`; this prefix is checked **before** the permission decision, because the rejected result carries `permission_decision {decision:"accept", source:"user_temporary"}` (`r1:95`: Tandem allowed the `can_use_tool`), and `ToolStates.isDenial` today answers `decision == "reject"` whenever a decision exists, which would leave the row `FAILED`) | none |
| after Stop | `ToolState.INTERRUPTED`: the CLI's synthetic result (`r2:43`) is `is_error:true` with the text `The user doesn't want to proceed with this tool use…` and `tool_result_meta:[{id, non_execution_kind:"user-rejected"}]`, **no** `permission_decision`. Today `Reducer` builds a `PermissionDecision` only when `permission_decision` is present (`Reducer.kt:807`), so the kind is lost and `ToolStates.of` would answer `FAILED` (`Failed to edit <file>` with the CLI's text). The reducer carries `non_execution_kind` into `ChatEntry.ToolResult` whether or not a decision exists (a new field `ChatEntry.ToolResult.nonExecutionKind: String?`, filled from the line's `tool_result_meta` entry for the block; `PermissionDecision` keeps its copy), and `ToolStates.of` maps an error result with `nonExecutionKind == "user-rejected"` to `INTERRUPTED` before the denial test | none |

The permission card does not appear for Tandem's tools: the `can_use_tool` is answered `allow` at once (4.2), the diff is the question. The `Accept all` state shows under the composer as the mode control's hint `Accepting all edits this turn` beside the mode name until the turn ends.

**The MCP panel and `/mcp`.** `mcp_status` lists the server as `{name:"tandem", transport:"sdk", scope:"dynamic", source:"sdk"}` (`r1:63`). Today `McpPanelModel.sourceOf` maps the unknown source `sdk` to `McpSource.OTHER` with the toggle and reconnect actions, and the own-server rule (`row`: `name == ownServer && source == "dynamic"`) would not fire, so the panel would show `tandem` as a foreign server the user can disable (`mcp_set_servers`), turning edits off silently. The rule becomes: `name == TANDEM_MCP_SERVER && source in {"sdk", "dynamic"}` is Tandem's own server, shown as the existing read-only own-server row (`readOnly = true`, no actions, the existing own-server pill text), under `McpSource.DYNAMIC`; `McpControls.toggleMcp` and `reconnectMcp` refuse that name with `McpResult.Failure("Tandem's own server cannot be changed")` whatever the caller. The `/mcp` slash palette entry and the CLI's own `/mcp` output list the server as the CLI does; nothing to change there. `Mcp.mcpStatus` ignores the new `transport` key (it reads named keys only), which `McpTest` asserts.

**The queue.** One diff at a time per project (`EditQueue` in `TandemEdits`, 5): calls queue in arrival order across the project's sessions; a queued call's row says so. The model of a session is blocked on its own call anyway, so the queue only matters with two live sessions editing at once. Stop in a session withdraws its queued calls (7.11); `Accept all` applies to the pressing session's later calls only.

### 3.5 Context: `@file` mentions and the selection

**`@` opens the file picker.** Typing `@` at the start of the composer or after a space opens a palette in the slash palette's compact form (`SlashPaletteView`, MCP spec 14; the same keys: Up / Down, Enter picks, Tab inserts, Esc closes until the draft changes): the project's files whose relative path matches what follows `@`, by the IDE's own matcher (`NameUtil.buildMatcher` over `FilenameIndex`'s names, read in a `readAction` off the EDT, debounced 100 ms, at most 40 rows, the open editors' files first). A pick replaces the typed `@…` with `@<path relative to the project base> ` (a trailing space). The pill `@path` stays plain text in the composer. The CLI expands it: the prompt's text block goes out as typed, and the CLI attaches the file from the disk, which the model sees without a tool (`r3:12`, `transcript.jsonl:6`, probes 3). Nothing shows on stdout for it; the bubble shows the text as typed, with each `@path` drawn as an inline chip when the path exists.

**A mentioned file with unsaved changes.** If, at send time, a mentioned path's `Document` is modified (`FileDocumentManager.getInstance().isDocumentUnsaved`), the CLI's disk read would be stale. Tandem then sends the mention as the bare path (no `@`, so the CLI does not expand it) and adds its own text block **before** the prompt's block: `<path> as open in the IDE, with unsaved changes (N lines):` and the buffer's text in a fenced block, at most 64 KB per file (beyond that the first 64 KB and the line `… truncated: <T> lines in all`). The bubble shows a chip `<name> (unsaved)`; the transcript reload recognises the block by its first line (`TranscriptReader`, 4.4) and draws the same chip.

**The selection.** While a text editor has a selection (at least one character, `SelectionListener` on `EditorFactory.getEventMulticaster()`, the editor the IDE reports as `FileEditorManager.selectedTextEditor`), the composer shows a chip above the text area: `<name>:<start>-<end>` (lines, 1-based, an ASCII hyphen) with an `×` (accessibility name `Remove the selection from the message`). Sending with the chip adds a text block before the prompt: `The user's selection in <path>, lines <start>-<end>:` (the same ASCII hyphen: the transcript reader matches on this first line, so the chip and the block use one form) and the selected text in a fenced block (64 KB bound as above). `×` drops the chip for this message; it comes back with the next selection. The chip is also in the bubble, and on reload. A selection in a diff editor or a console is ignored (`DiffUtil.isDiffEditor`, no `VirtualFile`). Nothing is sent when the chip is absent: the model never sees the selection by accident.

Both blocks are plain `text` blocks of the same `user` message (`HostMessages.userMessage` grows `context: List<ContextBlock>`), in front of the prompt's own block, as `user-image` records several blocks in one message (`docs/protocol.md` 3). A context-only message (chip, no text) is refused with the composer's existing empty-draft rule.

## 4. Data model

### 4.1 `protocol/` (every field validated; a mistyped frame is `Other`, never a throw)

**`initialize`** (`HostMessages.initialize`) gains `"sdkMcpServers":["tandem"]`:

```json
{"type":"control_request","request_id":"<id>","request":{"subtype":"initialize","hooks":null,"forwardSubagentText":true,"sdkMcpServers":["tandem"]}}
```

**`InboundRequest.McpMessage(serverName: String, message: JsonObject)`**, decoded from `{"subtype":"mcp_message","server_name":<string>,"message":<object>}` (`r1:1`, `:4`, `:6`, `:38`); a frame without a string `server_name` or an object `message` stays `Other` and gets today's `Unsupported request` error. The JSON-RPC inside: `method` (string), `id` (absent on a notification; a number in every recorded request, `0` to `3`, but JSON-RPC allows a string, so Tandem keeps it as a `JsonElement`, a number or a string, and never turns a string id into `Other`), `params` (object or absent). A `message` with no string `method`, or an `id` that is neither a number nor a string, is answered with the JSON-RPC error `-32600` (`Invalid request`) carrying the id when one exists, so the CLI never waits on it. `tools/call`'s `params` are `{name, arguments, _meta:{"claudecode/toolUseId": <tool_use id>, progressToken}}` (`r1:38`); `notifications/cancelled`'s are `{requestId, reason}` (`r2:41`).

**`HostMessages.mcpResponse(requestId: String, reply: JsonObject)`**:

```json
{"type":"control_response","response":{"subtype":"success","request_id":"<id>","response":{"mcp_response":<reply>}}}
```

where `reply` is a JSON-RPC response (`{"jsonrpc":"2.0","id":<id>,"result":…}` or `{"jsonrpc":"2.0","id":<id>,"error":{"code","message"}}`, the `id` echoed verbatim as the `JsonElement` the request carried), or for a notification `{"jsonrpc":"2.0","result":{},"id":0}` (what the Agent SDK answers, **binary**; `r1/sent.ndjson:5`).

**`TandemTools`** (pure Kotlin in `protocol/`, no IntelliJ): the server's answers.

| JSON-RPC `method` | Reply `result` |

| `initialize` | `{"protocolVersion": <the request's>, "capabilities": {"tools": {}}, "serverInfo": {"name": "tandem", "version": <plugin version>}}` (`r1/sent.ndjson:2`; the CLI asked `2025-11-25`, `r1:1`) |

### 4.3 The edit itself (`ide/edits/`, with a pure core in `session/edits/`)

## 6. Flows

**An edit, accepted with a hand change.** The model calls `mcp__tandem__edit_file` (`r1:35`) → `can_use_tool` (`:37`) → Tandem answers `allow` at once → `tools/call` (`:38`) → `ClaudeSession` hands the call to `IdeEditTools` on `Dispatchers.Default` → path and file checks on IO, the `Document` read in a `readAction`, `EditMatcher.match` → `TandemEdits.enqueue(proposal)` → the row reads `Reviewing <file> in the diff` → `EditDiff` opens on the EDT → the user edits the right side, presses Ctrl+S → `Accepted(finalText)` → on the EDT: the staleness check, the `WriteCommandAction`, `saveDocument` → `EditResults.accepted(...)` with the file's current text → `send(HostMessages.mcpResponse(...))` → the CLI writes the `user` tool result (`:41`) and the model goes on (`:57`), reading the disk that now holds the text. The row reads `Edited <file>` + `with your changes`.

**An edit, rejected.** As above until `Reject` with the reason → `ToolReply(isError = true)` → `r1:95`'s shape → the model answers (`:108`); the turn's `result` is a success with empty `permission_denials` (`:112`): the row is `Rejected edit of <file>` (DENIED), no permission card, no turn failure.

**Auto-accept.** `tools/call` → the checks → `ChatState.permissionMode` is `acceptEdits` → apply at once → `(auto-accepted)` result (`r2:68` under `acceptEdits`).

**Stop while the diff is open.** The user presses Stop → `interrupt` → the CLI sends `notifications/cancelled {requestId}` (`r2:41`) → `TandemEdits.cancel` closes the diff, the CLI writes its own synthetic result (`:43`: `is_error:true`, `non_execution_kind:"user-rejected"`, no `permission_decision`), which the reducer carries as `nonExecutionKind` and `ToolStates` maps to `INTERRUPTED` (3.4), the turn ends `aborted_tools` (`:45`), nothing is sent for the call.

**A mention.** The user types `@Foo` → the palette lists `src/main/kotlin/Foo.kt` → Enter inserts `@src/main/kotlin/Foo.kt ` → send → the text goes as typed → the CLI attaches the file (`transcript.jsonl:6`) → the reply. With unsaved changes in `Foo.kt`: the block of 3.5 goes first and the mention loses its `@`.

## 7. Errors and edge cases

1. **The file is not open in an editor.** `FileDocumentManager.getDocument(file)` loads a `Document` for any text file; the edit applies to it and Accept saves it to disk (3.2), and the file opens in no editor. The row's `Show diff` opened the diff only; a later click of the file name in the row opens the file (`OpenInEditor`, as today's rows do).
2. **A new file** (`write_file`, no such path): the diff shows `New file` on the left; Accept creates it (4.3). A path whose parent does not exist: the directories are created in the same command. A `write_file` for an existing file shows the whole file on both sides.
3. **The old string no longer matches** (the user edited the file, or the model never read it): the `NotFound` result with the buffer's text (4.3, `r2:104`: the model read it and did not retry). `Ambiguous` likewise. The match runs on the `Document`, so a buffer with unsaved changes is matched as the user sees it, not as the disk has it.
4. **Outside the project**: refused with the path rule (4.3); the project's base path and the session's added folders (`--add-dir`) are the roots, as the CLI's own tools have.
5. **Read-only**: `ensureFilesWritable` (VCS checkout or the IDE's "make writable" prompt, which is modal and on the EDT by the platform's design; it is the IDE's own dialog); a refusal is the read-only error. A read-only file system likewise.
6. **Very large**: `FileUtilRt.isTooLarge` (the IDE's own limit, `idea.max.intellisense.filesize` / `idea.max.content.load.filesize`) refuses the edit; the model is told the size. A `write_file` whose `content` is over 10 MB is refused the same way before any document is made.
7. **Binary**: `FileType.isBinary` (and `FileTypeRegistry.isFileOfType(file, UnknownFileType)` with a NUL in the first 8 KB) refuses the edit.
8. **A directory, a symlink**: a directory is refused; a symlink is followed (`toRealPath`) and must land inside a root.
9. **Plan mode**: the CLI's own `Write` is disallowed, so the model may try `write_file` for its plan file; Tandem refuses with the plan-mode text (4.3). Under `plan`, a `ExitPlanMode` approval switches the mode as today; edits start after.
10. **A `tools/call` while a diff of another session is open**: queued (3.4). A queued call's session stops: removed, no reply.
11. **Stop, close, the process dying**: Stop → `notifications/cancelled` (`r2:41`) → closed, no reply. The session closed or its process gone while a diff is open → `TandemEdits.cancel` for every call of that session, the diff closes with no reply (nobody reads it), the row shows the process's end as today. The project closing disposes `TandemEdits`, which closes any diff.
12. **The CLI does not take the server**: the version-gate notice (4.2). Also when `mcp_message` frames stop coming after `initialize` (a handshake the CLI gave up on): the same check on `init.tools` covers it.
13. **A JSON-RPC method Tandem does not serve** (`resources/list`, `prompts/list`, …): the `-32601` error. The CLI asked for none in the probes (`r1`, `r2`: `initialize`, `notifications/initialized`, `tools/list`, `tools/call`, `notifications/cancelled` only).
14. **Two calls for the same file in one turn**: each diff shows the file as it is when its turn comes, so the second proposal is matched against the first's applied text (the model sends the second call only after the first's result).
15. **The diff's window closed by the IDE** (project reload, "close all"): the file editor's disposal → `Rejected(null)` (3.1). A viewer switch inside the diff (side-by-side ↔ unified) changes nothing.
20. **The file changes while the diff is open** (the user types in the file, another session's accepted edit lands, a reformat runs): Accept's check inside the write command (3.2) refuses a stale proposal with the "file changed" result and the file's current text, writes nothing and shows the notice; the model retries against what it was given. The left side of a still-open diff keeps following the live `Document`, so the user sees the change before pressing Accept.
21. **The save fails** (disk full, the file became read-only after the write command): the edit stays in the buffer (undoable), the result tells the model it is unsaved (4.3), the notice says why.
16. **The result is huge** (a 64 KB file quoted): the bounds of 4.3; the model is told to `Read` the rest.
17. **A mention of a path that does not exist**: inserted as typed; the CLI's expansion of a missing path is **unrecorded** (probes 3): the bubble draws no chip for it.
18. **The selection is in the diff's right side**: ignored (3.5).
19. **`Accept all` then a `write_file` of a file outside the roots**: the checks come first; auto-accept never widens them.

## 8. Performance

The match and the result text run on `Dispatchers.Default`; file lookups on `Dispatchers.IO`; the only EDT work is the diff's construction and the write command, which the platform requires there. A 64 KB file numbers in under a millisecond; the Myers diff is bounded at 400 output lines and gives up (falls back to the whole-file block) past 20,000 input lines. The mention palette's candidate list is computed off the EDT and cached per project until the VFS changes (`VirtualFileManager` listener), at most 40 rows shown.
