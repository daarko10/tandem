## 1. Goal

The owner installed the branch in a 2026.1 IDE on a Mac and wrote, in short:

- a clamped body's `Show all` is permanent; it should be a toggle, and a collapsed row should reopen clamped;
- a running group hides its finished calls and a lone running call shows nothing, while the desktop app shows every call and which one runs;
- the intent-based autoscroll works (nothing changes there);
- the chat does not look like the desktop app: the mode and model pickers at the bottom, the text bar, Bash bodies with colour, "the text buttons";
- "I can't post pictures in the chat which is a big no no".

Eight decisions follow (section 2): live groups **[decision 1]**; no change to thinking **[decision 2]**, the owner confirmed afterwards that thinking streams correctly, so `ThinkingRowItem` and base §4.5 are untouched; `Show more` / `Show less` **[decision 3]**; the desktop composer and footer **[decision 4]**; Bash bodies **[decision 5]**; the inline code pill **[decision 6]**; the hover action row **[decision 7]**; image attachments **[decision 8]**. The cards' buttons stay as they are. One deviation from decision 4 stays open for the owner to accept: a session started without `--effort`, the common case, labels its model alone (`Sonnet 5.5`, where the desktop reads `Sonnet 5.5 Medium`) until the effort is read from the transcript's assistant lines (2.3 `<Effort>`, edge 14, open item 16, 2b). Hard rules: theme tokens only, plus editor scheme colours for code; never block the EDT; no product name of hard rule 8 in a UI string; every behaviour has a named test (section 7); nothing personal in committed files (the screenshots stay out of git).

Two colour tiers, as the desktop draws them: **secondary** ((195,194,184) on the desktop; `ChatPalette.secondary`, `text.normal` at 0.8 alpha **[proposal]**) for `Bash`, `$`, the Bash output, the `+`, the mode label and the model name; **dim** ((137,135,130); `ChatPalette.dim` = `text.info`, which Tandem already draws at that level: `tandem-01`'s `Thought for 7s`, `claude 2.1.300` and placeholder, `tandem-02`'s `Ran …` label) for the menu header, descriptions and digits, the effort, the context popover, the ring's track, the hover row's icons and its relative time. Base items drawn in `text.info` keep it (the thinking row is untouched, decision 2); the desktop draws its tool-row labels in the secondary tier too (desktop-01 `Checked rtk history…` samples (195,194,184)), and whether base's labels move up is the owner's call at the `runIde` check of both tiers in Dark and Light (open item 15).

## 2. What changes on screen

### 2.1 Running groups and running calls show every call with its state [decision 1]

**Evidence.**

- `tandem-02-bash-row-expanded.png` (2x): an opened done row `Ran grep -rniE "offline|refresh_?t…modules|worktrees" | head -30 ⌄` with its command box (≈558 dp wide) and output at a 17 dp line pitch; while a call of a group runs the group row cannot be opened (`canExpand(row)` is false for a running row, `ui/rows/ToolRowItem.kt`), so the finished calls are hidden until the last ends, and a lone running call has nothing to open.
- Ref §3.4: "rows exist from the moment the call starts" (stated S26), and the live step carries a coral dot (`• Opening in Browser`, `• Running npm test · 0/340 passed`; seen S3 desktop-browser-03, desktop-pop-out-03, -07). One sub-row per call with its own state, and a running call's body so far, come from that section and from decision 1; no owner capture shows a running group.

**What changes.** A group row opens in every state; its box lists one sub-row per call with that call's label (present participle while running, base §4.6.2), colour and chevron; the running call is marked, the finished ones plain. A lone live call opens when its input gives it a body so far, and draws the same marker before its label **[proposal]**: base §4.6.1's "no dot on top-level rows" is amended for lone rows, since the owner's complaint is exactly not seeing which call runs, and a lone running Bash or Read would otherwise differ from a finished one only by tense. A group header draws no marker **[proposal]**: its sentence ends with `…` and its open box marks the live call. Base §4.2's rule that `TandemColors.spark` belongs to the spark glyph alone is amended for this dot. The header keeps the base §4.6.4 rule-7 sentence with `…`; its chevron is enabled whenever the row opens.

- **Chevron rule** (one rule for `ToolLine`, so for rows and sub-rows alike): a row that opens draws the enabled chevron; a row that cannot open, live or finished, draws none. Today's disabled chevron on a live row goes: ref §3.4 describes the desktop's live step (`• Opening in Browser`) as "a small coral dot before the text, no chevron, for a live step", so the dot alone marks it.
- **Body contract.** Base §5.3's `ToolCall.body` comment (`ToolBody.None` while `PENDING`/`RUNNING`) is replaced by: the result-built body; else, while `RUNNING` or `WAITING`, `ToolBodies.pending(kind, input)`; else `None`, which a `PENDING` call always has.
- **A lone open call that joins a group.** Decision 1 makes opening a lone running call common (a `$ npm test` box). When the turn's next call joins it, the row becomes a group under the same key `tool:<first id>` (base §5.3), and `expanded(row key)` alone would show the box with every sub-row closed, the watched body folded away. Nothing is detected in composition (a `LaunchedEffect` in a `LazyColumn` item loses the previous size when the item is disposed, and sees the change a frame late): every call body's clamps are owned by `c:<call id>` wherever the body renders (2.2), and opening a lone row also sets `expanded("c:<its call id>")` (`ChatUiState.toggle(key, owners, opensWith)`, 3.4). A lone row that becomes a group therefore already has its sub-row open, with its `Show more` / `Show less` state, on the first frame and also when the item was off screen or another session was shown meanwhile.
- **Strings.** Unchanged labels; the box's sub-row labels are the calls' own.
- **Keyboard.** Unchanged: a row is a button, Enter or Space toggles it.
- **Measurements.** Sub-rows 36 dp, dividers 1 dp inset 8 dp, box radius 8 dp (base §4.6.1); the dot 6 dp, vertically centred, 8 dp before the label.
- **Stays.** Grouping, labels, the working row, the group's state colour, the unmarked group header; a lone running Read still does not open (no body), now drawn with the dot and no chevron.

### 2.2 `Show more` / `Show less`, and a collapsed row reopens clamped [decision 3]

**Evidence.** Today `Show all N lines` sets `ui.expanded("all:<call id>")` to true and nothing resets it (`ui/rows/ToolBodyView.kt` `Clamped`). The desktop shows Bash output in full (ref §3.5 Bash), so the toggle is Tandem's own **[proposal]**, worded like the user bubble's `Show more` / `Show less` (base §4.3).

| Body state | Link under or after the body | Click |
|---|---|---|
| clamped (over 20 lines or 240 dp, base §4.7) | `Show more` | opens |
| opened | `Show less` | clamps again |
| opened, then its row, its group or its Agent row collapsed | — | the next open is clamped |

- **Clamp ownership.** A clamp is registered under its call's owner `c:<call id>`, wherever the body renders: a lone row, a group sub-row, a nested row inside an Agent body (an Agent call's body is its nested rows, whose calls own their clamps the same way). Collapsing a row resets the clamps of every owner beneath it: `c:<id>` of each call in `row.calls` and, for an Agent call, of its nested rows' calls, recursively (`clampOwners(row)`, pure, 3.4). Collapsing a sub-row resets `c:<id>`'s clamps. A lone row that becomes a group keeps them, under the same owner (2.1). The sub-rows' own `expanded("c:<id>")` is kept **[proposal]**: a reopened group shows the sub-rows that were open, each clamped again.
- **Strings.** `Show more`, `Show less`, `… N more lines` (unchanged, after the 400-line cap).
- **Keyboard.** The links are Jewel `Link`s: Tab reaches them, Enter follows.
- **Stays.** The clamp rule, the fade, bodies that clamp by height only (Markdown, links), the command box's own 20-line clamp (part `command`, 2.4).

- **Words.** A word runs to unquoted, unescaped whitespace or an operator; quotes inside a word are part of it (`--include='*.js'` is one `ARGUMENT`); `"…"` takes `\"` escapes, `'…'` is literal; an unbalanced quote runs to the end of the command; no operator is recognised inside quotes. A backslash outside quotes escapes the next character into the word (`\;` is part of an `ARGUMENT` and does not end the command; `a\ b` is one word); only `\` + newline is a `PLAIN` continuation. `{`, `}`, `(` and `)` are operators only where the table says; elsewhere they stay inside their word: `${HOME}`, `$((…))` (arithmetic, not a `$(`), brace expansion `a.{js,ts}`, `find`'s `{}`, and `NAME=(…)`, whose parentheses and inner spaces belong to the assignment word.
- **Several lines** (the CLI's commands are often multi-line). A newline outside quotes and heredocs ends the simple command like `;` (the newline itself is `PLAIN`). A `\` before a newline continues the line (`PLAIN`, the command position does not reset). After `<<` or `<<-` and a delimiter word (`EOF`, `'EOF'`, `"EOF"`; quotes stripped for the match), the rest of that line tokenises as usual, and the following lines up to and including the line that is the delimiter alone (leading tabs allowed after `<<-`) are one `PLAIN` token, never commands or flags; an unterminated heredoc runs to the end. `$(` … `)` and backticks outside quotes open and close a nested command whose first word is a `COMMAND`; inside double quotes they stay part of the `ARGUMENT` **[proposal]**, so the CLI's usual `git commit -m "$(cat <<'EOF' … EOF)"` reads as one green argument and its message is not coloured as commands.

Both keys always carry a foreground in the bundled schemes, so the fallbacks serve only a scheme that gives none.
- Colours are read in `chatPalette()` (`remember(JewelTheme.instanceUuid)`, base §4.2) with `scheme.getAttributes(key)?.foregroundColor?.toComposeColor()`, else the fallback (`schemeColor(attributes, fallback)`, pure, 3.4).
- **Clamp.** The token ranges are computed once over the full command, off the EDT, where the body is built (`ToolBody.Command.tokens`, 3.3; base §5.3); composition only maps kinds to colours; the command box's 20-line clamp (2.2, part `command`) cuts the built `AnnotatedString` at the end of the 20th line (`commandText`, pure, 3.4), so a clamped heredoc keeps the colours it has in full.

### 2.8 Question card: Next and Submit answers

**Evidence.** `tandem-06-question-card.png` (2x): the card of base §4.13 as built (T10, T11), with the tabs `Refresh token` and `Error logs ·`, three options with the caps `1`–`3`, `Other` with its `Something else…` field, and the buttons `Cancel Esc` and `Submit answers ↵`. The owner, after using it: "This looks sick!!! One problem, when answering the submit answers should show next if there are more questions and the submit answers when everything is filled, currently I need to click and then click again in the second tab, that reduce productivity as I need to reach for the mouse". Today (`ui/cards/QuestionCardView.kt`) the primary button always reads `Submit answers`, disabled until every question has an answer (`picksOf != null`); the next tab is reached with the mouse, or with `→` only while the strip has the focus; Enter is `Submit answers` and does nothing until then. So on a two-question card the keyboard user picks, reaches for the mouse, clicks the second tab, picks, and clicks or presses Enter.

**What changes.** The primary button (the `DefaultButton` with the `↩` cap) is one of two, decided by the pure `questionPrimary(answered, tab)` (the delta below) from which questions have an answer and which tab is shown:

- `Next` **[the owner's string]**, while at least one *other* question (any but the shown one) has no answer. Always enabled. A click, or Enter, shows the next unanswered question after the shown one in tab order, wrapping to the first tab, and moves the keyboard focus to that question's first row (`defaultFocus`, the requester the card uses when it opens), so the next digit picks at once; the strip's tab follows as a click on it would.
- `Submit answers`, once every other question has an answer: enabled when the shown one has too (every question answered, as today), disabled otherwise; a click, or Enter, submits.

An answered question is one with a non-blank `Other` text or at least one picked option: the rule `picksOf` and the tab marker (`tabLabel`) already use. Picking an option never advances by itself (a one-answer question included): the user confirms with Enter, which is also what makes a mis-typed digit cheap to fix. The dot after a tab's header still marks an unanswered question (base §4.13).

| Questions | Shown question | Other questions | Primary | Enabled | Enter, or a click on it |
|---|---|---|---|---|---|
| 1 | unanswered | — | `Submit answers` | no | nothing |
| 1 | answered | — | `Submit answers` | yes | submits |
| 2+ | unanswered | one or more unanswered | `Next` | yes | shows the next unanswered question after the shown one, wrapping |
| 2+ | answered | one or more unanswered | `Next` | yes | the same |
| 2+ | unanswered | all answered | `Submit answers` | no | nothing |
| 2+ | answered | all answered | `Submit answers` | yes | submits |

- **Keyboard.** Enter anywhere on the card outside the `Other` field (`CardFrame`'s `onEnter`) and Enter in the `Other` field (`QuestionKey.Primary`, which replaces `QuestionKey.Submit`) run the primary, `Next` or `Submit answers`; Shift+Enter in the field still inserts a newline; Cmd/Ctrl+Enter still does nothing (base §4.18). `1`–`9` pick as today, outside the field. `←`/`→` on the strip as today. **Edge cases.**

1. **One question.** No strip; the primary is `Submit answers` throughout, as today; `questionPrimary` never returns `Next` for a one-element list.
2. **`Other` selected with an empty field.** Not an answer (`picksOf`, the tab's dot): with another question unanswered, Enter in the field is `Next` and moves on, the tab keeps its dot; with every other question answered, the primary is `Submit answers`, disabled, and Enter does nothing, as today.
3. **A multi-select question with nothing picked.** Unanswered, as above; a pick that toggles the last picked option off makes it unanswered again: an enabled `Submit answers` becomes disabled at once, and a `Next` stays (edge 7).
4. **The last tab answered first.** The flow above: `Next` wraps from the last tab to the first unanswered one.
5. **Three questions, the middle one shown, the first and third unanswered.** `Next` shows the third (the next after the shown one), not the first; from the third, `Next` wraps to the first.
6. **A tab clicked with the mouse.** Shows that question as today; the focus stays where it was (`focusNext` is set by `Next` only).
7. **An answered question edited back.** Clearing the shown question's `Other` text, or toggling its last multi-select pick off, turns an enabled `Submit answers` into a disabled one on the next recomposition (`others` is read in composition). `Next` never appears from an edit, because it depends only on the other questions, which an edit to the shown one cannot change.
8. **Enter on a focused option row.** Runs the primary, never toggles the row (the keyboard rule above). ## 4. Flows

- **A running group, opened while calls finish.** `Read a.kt`, `Read b.kt` done, a Bash call running: the row reads `Read 2 files, running a command…` and opens; the box lists `Read a.kt ›`, `Read b.kt ›` and `• Running tests` with the spark dot and an enabled chevron (its body so far is the `$ npm test` box). The user opens the Bash sub-row: the command box (a sub-row's body has no `Bash` header and no frame, 2.4), no output. Text deltas of the turn rebuild it without rebuilding that body (`pendingBodies`, same input instance). The result lands: the builder rebuilds the turn; the Read calls keep their `ToolCall` instances (their sub-rows skip), the Bash call is new (`DONE`, output filled), the group row is a new instance with the sentence `Read 2 files, ran a command`; `expanded("tool:<first id>")` and `expanded("c:<bash id>")` are untouched, so the box stays open and the output appears in place; the working row moves on.
- **A lone open call that joins a group.** A lone Bash call runs; the user opens it and watches `$ npm test`. Opening the lone row set `expanded("c:<bash id>")` too. A Read call starts: the row key stays `tool:<bash id>`, now a group of two; the box is open with the Bash sub-row already open (`c:<bash id>`), its `Show more` state the same (its owner was `c:<bash id>` throughout), and the Read sub-row closed; nothing reacts to the change in composition.
- **Show more, collapse, reopen.** A 200-line Read body opens clamped at 20 lines with `Show more`; the click sets `clampOpen("c:<id>", "body")`; the body shows all 200 lines and ends with `Show less`; the user clicks the row: `ui.toggle("tool:<id>", clampOwners(row), opensWith = "c:<id>")` closes it and resets the clamp; the next click shows 20 lines and `Show more` again. In a group, the same click on the group row also resets each sub-row's `c:<id>` clamps; a sub-row that was open is open again on the next open, clamped.
- **Picking a mode and a model.** Click `Manual`: the menu opens above it with `Manual` checked beside its `2`; `4`: `set_permission_mode plan` goes out, the label reads `Plan` at once (`permissionModeChanges`), the CLI's `system/status` confirms; a rejection puts `Manual` back with the notice. On a session like agent-sync (Sonnet 5.5 runs, `Fable 5.1` carries the `Default` chip) click `Sonnet 5.5`, pick `Opus 5.5`: `set_model opus`, the label reads `Opus 5.5`; the next `init.model` confirms or warns (base hard rule 5). Picking `Fable 5.1` there sends `set_model fable`, not null, since Sonnet runs. `Effort ›`, `High`: `apply_flag_settings {effortLevel:"high"}`, the label reads `Opus 5.5 High`; an error answer restores the previous level and shows `Effort not changed: …`. On a stopped session the same pick only sets the effort, and the next spawn passes `--effort high`.
- **The ring after a result.** The first `message_start` of a turn carries `inputTokens` (`Ndjson.inputTokens` sums input, cache creation and cache read); the reducer sets `context.tokens`. The `result` carries `modelUsage[<model>].contextWindow`; the reducer sets `context.window`. `ChatPresenter.context` changes once per API call; only `ContextRing` collects it, so it recomposes alone and `ComposerModel` does not change. Before the first result the window is unknown and the ring is hidden; after it each later `message_start` moves the arc.
- **Sending an image.** `Cmd+V` with a screenshot on the clipboard: `composerKey` returns `PasteImage`; `readClipboardImages()` runs on IO (the AWT image encoded as PNG), the thumbnail decodes on Default, `attachments` gains a `PendingImage` on the EDT; the strip shows it as `[Image #1]`. Enter: on the EDT the handler captures the text and the attachments, clears the draft and the strip and sets the sender's `sending`; `ComposerSender` encodes base64 on Default, calls `manager.send(id, text, images)` and clears `sending` (until then Enter does nothing and the Send button is disabled); `ClaudeSession` dispatches `UserSent(images)` (the bubble renders at once with an `[Image #1]` placeholder above the text; the presenter's decode posts the thumbnail and the row re-renders with it) and writes the frame; the reply streams as usual.
- **Fork from the hover row.** Hover the latest reply once its turn ended: the row fades in; `Fork from here`: `SessionActions.fork(id)`, which runs `SessionManager.fork(id)` on the project's scope; the fork is selected (the sessions spec's flow); null adds the notice to the chat.

## 5. Edge cases

1. **No models in the init yet.** The model control reads the `activeModel` wire id, or `Model` before anything is known; the mode control reads `Mode` until the first `init` or a pick, checking no entry; its menu has no model items; `Auto` is listed only as the checked current mode; `Effort ›` appears only when `ChatState.effort` is known, listing `low`, `medium`, `high`, `max` **[proposal]** until the levels arrive; with neither, the menu holds no `Effort` item.
2. **A mode the CLI does not list or Tandem does not offer.** `bypassPermissions` or `dontAsk` reported by `init`: the control shows `Bypass permissions` / `Don't ask`, the menu lists it checked without a digit; picking `Manual` sends `default` as today. A `set_permission_mode auto` rejection (the `permission-mode-rejected` shape) restores the previous label with the error notice (open item 2). `auto` on a model without `supportsAutoMode`: listed checked, with its `1`, while current.
3. **Unknown context window.** No `result` yet, or a `modelUsage` without `contextWindow`: the ring is not drawn and nothing else moves. Tokens known but no window after a result: still hidden, no popover text. A reloaded transcript knows neither (assistant lines' `usage` is not decoded, open item 7).
4. **A command with unbalanced quotes.** `echo "a | b` tokenises as `COMMAND echo`, `PLAIN` space, then `ARGUMENT "a | b` to the end: no `OPERATOR` inside an open quote, never an exception. An empty command gives `[]`; `||` alone gives one `OPERATOR`.
5. **A group mixing a failed and a running call.** Base §4.6.4 rule 3 holds: the failed call is its own red row, the calls after it form a running group of their own; a `DENIED` call while another waits likewise. A running group whose only live call is `WAITING` reads in `text.warning` with the warning dot on that sub-row.
6. **Narrow pane (350 px).** Footer: the mode at the start, the model label ellipsised (`Opus 5.5 Ex…`), the ring always visible; thumbnails wrap; the command box wraps its line as today and the tokens keep their colours across the wrap.
7. **Redacted or broken image data.** A transcript's `data: "<base64>"` (the redactor's placeholder for long data, `scripts/redact_fixture.py`) or a corrupt PNG: `Base64.decode` or `Image.makeFromEncoded` fails inside `runCatching`; the bubble draws the `[Image #N]` placeholder; the log names the type and index only.
8. **Images only, no text.** Enter sends the image blocks alone; the bubble shows the thumbnails with no text box; on reload the line still yields its entry (text `""`), and as a first prompt it titles the session `[Image #1]`.
9. **Text and an image on the clipboard at once** (a rich-text copy from an Office, Excel or Numbers cell, some editors): the text wins and pastes as today, with no attachment; only an image without text, or a file list holding image files, attaches (2.7; open item 8).
10. **Send while a turn runs, or while the previous prompt is still encoding** (`sending`, 2.7). As base §4.15: Enter does nothing and the Send button is disabled (dimmed); both go through `sendDraft`, which checks the sender's own flag, so a click that races the encode sends nothing; the text and the attachments stay in the composer.
11. **Fork before the first turn completed.** The transcript does not exist yet; `fork` returns null and the notice of 2.6 shows.
12. **A running lone Read.** `ToolBody.None`, no children: the dot and no chevron (ref §3.4), the row does not open.
13. **Large images.** The encoded total is capped at 30,000,000 bytes (2.7), so a message stays under the 32 MB request; `ComposerSender` encodes on Default and the composer stays responsive; the state holds the strings until the entries go (section 6).
14. **Effort null.** The label shows the model alone; the `Effort` row's trailing text is `Default`, nothing checked on the effort page (open item 16: the transcript's effort, 2b).
15. **A model without effort support** (`Haiku 4.5`): no separator, no `Effort ›`, no effort in the label.
16. **A switch to a model that lacks the current level** (`xhigh` → `Opus 4.6`): the label keeps `Extra high`; the effort page lists it last, checked and disabled.
17. **A multi-line command.** Each line's first word after a newline is a `COMMAND`; a heredoc's body lines are `PLAIN`; a clamp at 20 lines keeps the colours of the full tokenisation.
18. **A reloaded transcript with unfinished calls.** They are `INTERRUPTED` and keep `None`: they do not open.
19. **Braces, parameter expansion and escapes.** `echo ${HOME}/x` is `COMMAND echo` and one `ARGUMENT`; in `find . -name '*.md' -exec grep x {} \;` the `{}` and `\;` are `ARGUMENT`s, so the command position does not reset (and `grep`, after `-exec`, is an argument); `cp a.{js,ts} b` has two `ARGUMENT`s; `{ a; }` and `(cd x)` open a group and a subshell whose first words are `COMMAND`s.
20. **Settings force another model than the default** (agent-sync): the label and the `✓` follow `init.model` (`Sonnet 5.5`); the `Default` chip stays on `Fable 5.1`, whose pick sends `set_model fable`.
21. **An assistant line without a timestamp** (a reloaded transcript): the reducer maps the reader's `0` to a null `atMillis`; the hover row shows Copy and Fork without a relative time or its tooltip, never `20383 days ago`.

## 6. Performance

- A state change of one call rebuilds the live turn's rows (base §9). With `liveCalls` the unchanged `ToolCall` instances are reused, so in an open group only the changed sub-row recomposes (strong skipping compares unstable parameters by identity); the group header `Text` recomposes once per sentence change; `ToolBodyView` of the changed call once when its body changes. The dot is a 6 dp `Box`, not animated.
- Pending bodies are cached by the identity of `block.input` (`pendingBodies`, swapped per build like `bodies`), so the text and thinking deltas, `task_progress` and `thinking_tokens` lines that rebuild the live turn do not rebuild them: a pending body is built once per input instance, and the reused body lets `liveCalls` compare the `ToolCall` identity-fast. Base §5.3/§9's "a result's body is built once" extends to pending bodies.
- `ChatUiState.clampOpen` keeps one `MutableState` per body part; a reset writes only the collapsed row's owners' states.
- `ChatPresenter.context` changes on `message_start` and `result`, never per token, and only `ContextRing` collects it; `ComposerModel` holds no context, so the mode and model controls, `ChatPane` and the prompt box do not recompose for it. `PromptBox` takes only `busy`, `sending` and `cardOpen`.
- The hover row's visibility is a `hoverable` interaction state local to the item; its 60 s ticker is one `LaunchedEffect` per composed row (one per ended turn); `ReplyHost`'s `latestReply` and `busy` states are read inside `MessageActionsRow` only (a `derivedStateOf`), so a turn's start or end recomposes the action rows, never the text rows.
- Thumbnails: decoded once per image id in child coroutines on `Dispatchers.Default` with bounded parallelism, outside the render loop (3.4), so a 100-image message or a reloaded transcript never holds back the reply stream; scaled to a longest side of 480 px (≤ 1 MB each), cached by id and dropped when their row's key disappears; the composer strip keeps full bytes (≤ 3.75 MB each) until the send, then drops them.
- `ShellTokens.tokenize` runs off the EDT where the body is built, once per body (`ToolBody.Command.tokens`), never in composition (a command can reach the 50,000-character body cap); the view maps kinds to colours in `remember(tokens, palette)`.
